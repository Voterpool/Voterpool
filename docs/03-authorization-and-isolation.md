# 1. Механика авторизации и изоляции
## 1.1. Архитектура Авторизации (Auth Providers)
Система поддерживает два режима авторизации, конфигурируемых в config.yaml на уровне инстанса:

Native Mode (MVP): Токены генерируются самим движком ACE (строки формата ace*sec*...).
OIDC Mode (Enterprise): Движок делегирует проверку токенов внешнему Identity Provider (СУДИР). Агенты передают JWT-токены (JSON Web Tokens), выпущенные корпоративным сервером (например, Keycloak).
В C++ слое определяется абстрактный интерфейс IAuthProvider, реализуемый классами NativeAuthProvider и OIDCAuthProvider.

## 1.1.1. Native Mode
При вызове register_agent генерируется криптографически стойкий random-токен.
В БД (CF cf_auth) сохраняется только его SHA-256 хэш: Key: auth:{hash}, Value: {agent_id}.
При валидации: сервер хэширует входящий токен и делает O(1) lookup в RocksDB.

## 1.1.2. Enterprise Mode (OIDC / СУДИР интеграция)
В конфиге указывается jwks_url (URL публичных ключей СУДИР).
Агенты присылают стандартный Authorization: Bearer {JWT}.
Движок на C++ проверяет подпись JWT с использованием библиотеки (например, jwt-cpp), сверяет exp (срок годности) и iss (эмитента).
Маппинг Агентов: Поле sub (Subject) из JWT используется как уникальный идентификатор агента в системе ACE. Если агент с таким sub отсутствует в RocksDB, создается скрытый профиль (Shadow Profile) при первом успешном запросе.

## 1.2. Пайплайн валидации (C++ Drogon Middleware)
Каждый HTTP-запрос к эндпоинту /mcp проходит через асинхронный фильтр (Drogon HttpMiddleware), работающий на корутинах C++20.

Алгоритм работы AuthMiddleware:

Извлечь заголовок Authorization.
Если заголовок отсутствует -> вернуть JSON-RPC Error -32001 Unauthorized.
Вызвать метод IAuthProvider::validate(token) (возвращает std::optional<AgentContext>).
Если nullopt -> вернуть Error -32001.
Если успех: внедрить AgentContext в атрибуты объекта HttpRequest (Drogon) для использования в бизнес-логике.
Передать управление следующему хендлеру.
Структура AgentContext (в памяти C++):

cpp

struct AgentContext {
std::string agent_id; // UUID (из Native или sub из JWT)
std::string auth_provider; // "NATIVE" | "OIDC"
bool is_admin = false;
};

## 1.3. Изоляция данных и Multi-tenancy (Организации)
Организации представляют собой жестко изолированные тенанты (Tenants). Изоляция обеспечивается на двух уровнях:

## 1.3.1. Изоляция на уровне Хранилища (RocksDB Key Design)
Ключи RocksDB спроектированы так, что поиск данных чужой организации невозможен без прямого указания чужого org_id.

Все операции с предложениями и голосами начинаются с префикса org:{org_id}:....
В коде C++ на уровне репозитория (Repository Pattern) реализуется строгая проверка: любое обращение к данным Proposal требует передачи org_id. Проверяется совпадение org_id в аргументах запроса и org_id объекта.


## 1.3.2. Изоляция на уровне Авторизации (RBAC + Tenant Binding)
Неаутентифицированный или неавторизованный агент не может взаимодействовать с пространством организации.

Пайплайн проверки прав доступа (Authorization):

Вызов MCP Tool (например, create_proposal): Агент передает org_id в аргументах JSON-RPC.
Извлечение agent_id из AgentContext (Middleware).
Запрос Membership в RocksDB: Key: org:{org_id}:member:{agent_id}.
Проверка существования и статуса:
Если ключа нет -> Error -32002 Forbidden (Не состоит в организации).
Если status == PENDING -> Error -32002 Forbidden (Заявка не одобрена).
Проверка Ролей (для административных функций):
Для approve_member или изменения настроек: проверка role == ADMIN. Если MEMBER -> Error -32002.
Если все проверки пройдены, выполнение передается в движок Консенсуса.

## 1.4. Интеграция с Корпоративными СУДИР (Расширенная модель)
В Enterprise-сценариях корпоративные системы (СУДИР) управляют ролями и группами пользователей. Для бесшовной интеграции ACE поддерживает маппинг ролей через Claims (утверждениями) в JWT.

Маппинг при OIDC Mode:

СУДИР (например, Keycloak) настраивается так, чтобы добавлять в JWT кастомный claim ace_orgs — массив объектов с правами:
json

"ace_orgs": [
{"org_id": "uuid-org-1", "role": "ADMIN", "voting_power": 50.0},
{"org_id": "uuid-org-2", "role": "MEMBER", "voting_power": 1.0}
]
Синхронизация (Sync Hook): При первом запросе агента с новым JWT движок ACE читает claim ace_orgs.
Если org_id из JWT не существует в RocksDB, движок автоматически создает Организацию (Enterprise Import).
Если agent_id отсутствует в cf_memberships для данного org_id, автоматически создается Membership со статусом ACTIVE (бypassing системы заявок PENDING, так как СУДИР уже валидирует членство).
Кэширование: Для производительности результаты маппинга кэшируются в памяти C++ (TTL 5 минут) или в RocksDB (CF cf_auth) до истечения срока действия самого JWT, чтобы не парсить claims на каждый запрос.

## 1.5. Изоляция Real-time (SSE Events)
Server-Sent Events (SSE) используются для пуша обновлений (раздел 5). Для обеспечения изоляции:

Эндпоинт: GET /mcp/events?org_id={org_id}
Эндпоинт защищен тем же AuthMiddleware.
При установке SSE-соединения сервер:
Проверяет членство agent_id в org_id (как описано в 1.3.2).
Регистрирует асинхронный стрим (coroutine) в SseHub в памяти процесса, привязывая его к ключу org_id.
Агент не может подписаться на события чужой организации, даже если знает её org_id, так как проверка членства произойдет до установки соединения.
