OpenSpec: Резервное копирование и Disaster Recovery (RocksDB Checkpoints)
Версия: 1.0.0
Статус: Draft

# 1. Проблема

RocksDB хранит всё на локальном диске (Shared-Nothing, docs/00 NFR-3). Потеря сервера без бэкапа = потеря всех организаций, истории голосований и настроек консенсуса. Копирование файлов «на горячую» через cp/tar поверх живой директории ДАННЫХ даёт повреждённый снимок: SST-файлы мутируют компакцией в момент копирования.

# 2. Механизм: RocksDB Checkpoints

Единственный разрешённый способ снимка — rocksdb::DB::CreateCheckpoint(dir):

Создаёт СОГЛАСОВАННЫЙ point-in-time снапшот: жёсткие ссылки на неизменяемые SST-файлы + консистентная копия MANIFEST/CURRENT.
Работает на живой БД без остановки записей (мгновенная операция на уровне метаданных).
Каталог снапшота можно свободно архивировать (tar) и переносить в объектное хранилище (S3-compatible).
Guard: если БД не открылась либо её статус содержит Corruption — команда ОТКАЗЫВАЕТСЯ делать снимок (бэкап больной БД бесполезен; связь с db_healthy_ — docs/07 §1.5).

# 3. CLI (MVP)

Использование:
text

./voterpool checkpoint --config /etc/voterpool/config.yaml --path /backups/snapshot_123
Порядок работы команды: парсинг конфига → открытие БД в offline-режиме (воркеры и HTTP НЕ поднимаются) → CreateCheckpoint(path) → закрытие БД → exit(0); любая ошибка → stderr + exit(1).

Конфликт локов: если движок запущен на той же storage.path, второй процесс получит ошибку LOCK («engine is running on this path»). В MVP команда выполняется на ОСТАНОВЛЕННОМ движке (или на копии/реплике каталога данных).

# 4. Enterprise (Cloud)

По крону: встроенный планировщик вызывает CreateCheckpoint на живом хэндле основного процесса и стримит каталог снимка в S3; политика retention — вне ядра.
Онлайн-альтернатива без остановки основного процесса в стороннем скрипте: RocksDB Secondary Instance (вторичная реплика каталога), checkpoint снимается со вторичной инстансы. Зарезервировано для Enterprise-редакции.

# 5. Процедура восстановления (Restore)

Остановить движок (на узле-замене — убедиться в отсутствии процессов).
Переименовать/очистить текущий storage.path (старый каталог сохранить для форензики).
Скопировать содержимое снапшота в storage.path (cp -a).
Запустить движок: MANIFEST/WAL из снапшота гарантируют консистентность; meta:schema_version из снапшота проходит штатную процедуру миграций, если бинарник новее (docs/12 §5).
Restore-учение автоматизировано тестом tests/integration/test_checkpoint_restore.cpp (docs/10 §2.2): снять checkpoint во временную директорию → развернуть в новую → открыть → все данные читаемы.

# 6. RPO / RTO

Снапшот — точка во времени: голоса между снимками при потере диска теряются; RPO = интервал бэкапов, RTO = время copy + restart. Инкрементальные бэкапы и непрерывная архивация WAL — Enterprise-функции.
