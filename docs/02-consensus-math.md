# 1 Точная математика алгоритмов консенсуса

## 1.1. Архитектура модульности (Consensus Strategy)

Для поддержки произвольных моделей принятия решений система использует паттерн Strategy.
В C++ ядре определяется абстрактный базовый класс IConsensusModel. Каждая модель консенсуса реализует интерфейс и регистрируется в фабрике (Factory) по строковому идентификатору. Это позволяет добавлять новые алгоритмы (например, Квадратичное голосование, Вето) без изменения бизнес-логики системы.

C++ Интерфейс:

cpp

struct ConsensusState {
ProposalStatus status; // ACTIVE, PASSED, REJECTED
bool consensus_reached;
};

class IConsensusModel {
public:
virtual ~IConsensusModel() = default;
virtual ConsensusState evaluate(
const Proposal& proposal,
const OrganizationConfig& config
) const = 0;
// Набор допустимых вариантов голоса — СВОЙ у каждой модели (см. 1.1.1)
virtual const std::set<VoteDecision>& allowed_decisions() const = 0;
};

## 1.1.1. Наборы вариантов голоса (Per-Model Decisions)

Каждая модель консенсуса определяет СОБСТВЕННЫЙ набор допустимых вариантов голоса. McpHandler валидирует decision по allowed_decisions() модели организации; недопустимый вариант — ошибка -32005 Business Rule Violation.

Модель | Варианты | Семантика неявки / воздержания
MAJORITY | YES, NO | Неявевший = ПРОТИВ (порог считается от полной силы T); ABSTAIN отсутствует — воздержание здесь неотличимо от неявки
QUORUM_PERCENTAGE | YES, NO | Не сделавший vote просто не учтён: явка V = Y + N; ABSTAIN отвергается (-32005)
CONSENT | YES, NO, ABSTAIN | ABSTAIN = «не против, но и не за»: увеличивает voters_count, но не влияет на N

Примечание: поле abstain_power в схеме Proposal (docs/01 §2.4) остаётся общим для всех моделей; у моделей без ABSTAIN оно всегда 0.

## 1.2. Распределение силы голоса (Voting Power)

Организация имеет поле power_distribution, определяющее, как рассчитывается voting_power агентов.

## 1.2.1. Модель EQUAL (Равная)

Логика: Каждый активный участник имеет силу голоса 1.0.
Общая сила (total_voting_power): Равна количеству участников со статусом ACTIVE.
Обновление: При вступлении/выходе агента total_voting_power инкрементируется/декрементируется на 1.0.

## 1.2.2. Модель SHARES (Доли)

Логика: Сила голоса агента задается ADMINом в виде дробного числа (например, 45.5).
Общая сила (total_voting_power): Равна сумме voting_power всех ACTIVE участников.
Ограничение: При power_distribution == SHARES модель CONSENT (требует подсчета голов) может быть неэффективной, но математически допустима.
Обновление: При любом изменении voting_power участника, total_voting_power организации пересчитывается инкрементально: new_total = old_total - old_power + new_power.

## 1.3. Полный флоу жизненного цикла принятия решений

Шаг 1: Вступление и регистрация сил
Агент создает организацию. В create_organization передается config.
Создатель получает role: ADMIN. Если EQUAL, его voting_power = 1.0. Если SHARES — voting_power = 100.0 (контракт create_organization не принимает начальное значение силы, см. docs/05 §1.2).
total_voting_power организации инициализируется силой создателя.
Шаг 2: Создание Предложения (Proposal)
Агент (ACTIVE или ADMIN) вызывает create_proposal.
Вычисляется expires_at = created_at + config.voting_duration_sec.
Агрегированные счетчики инициализируются: yes_power = 0, no_power = 0, abstain_power = 0, voters_count = 0. В объект Proposal сохраняется snapshot суммы сил участников на момент создания: total_voting_power_at_creation = T. Все дальнейшие расчеты консенсуса используют эту "замороженную" сумму, чтобы вступление новых участников во время голосования не ломало математику. T остаётся НЕИЗМЕННОЙ до закрытия предложения.
Предложение сохраняется в БД со статусом ACTIVE.
(Опционально) Сохраняется config_delta.
Шаг 3: Голосование (cast_vote) и Пересчет
При каждом вызове cast_vote происходит атомарная транзакция (WriteBatch в RocksDB):

Проверка, что Агент ACTIVE и еще не голосовал.
Фиксация power_at_vote из Membership.
Инкремент соответствующего счетчика в Proposal:
decision == YES -> yes_power += power_at_vote
decision == NO -> no_power += power_at_vote
decision == ABSTAIN -> abstain_power += power_at_vote
voters_count += 1
Вызов Evaluation Engine: В памяти C++ вызывается IConsensusModel::evaluate(proposal, config).
Если consensus_reached == true, статус Proposal меняется на PASSED или REJECTED. Транзакция коммитится.
Если false, статус остается ACTIVE. Транзакция коммитится.
Шаг 4: Истечение таймера (Background Worker)
Отдельный фоновый поток (Worker) проверяет expires_at < current_time.

Если время вышло, вызывается IConsensusModel::evaluate для финального расчета (проверка кворума по итогам).
Статус меняется на PASSED, REJECTED или EXPIRED.
Шаг 5: Применение последствий PASSED (config_delta и ACTION)
Если статус PASSED:
config_delta != null → новые настройки консенсуса применяются к Organization (в силе для всех будущих предложений; текущие активные продолжают жить по старым правилам).
proposal.type == ACTION → выполняется действие action.kind в транзакции закрытия предложения:
APPROVE_MEMBER: target_agent_id переводится из PENDING в ACTIVE (total_voting_power инкрементально, cf_agent_orgs создаётся, ключ pending: удаляется, join_limit: инкрементируется). Если участник уже не PENDING — действие пропускается (идемпотентно).
UPDATE_ORG_INFO: дельта метаданных применяется к Organization (updated_at = now); затронутые поисковые индексы (org_name:, tag:, category:) переиндексируются в том же WriteBatch — поиск никогда не видит промежуточного состояния.
Действия применяются либо обработчиком голосования (досрочный PASSED), либо TTL-воркером (закрытие по таймеру) — единая точка применения.

## 1.4. Точная математика встроенных моделей

Переменные:

Y = yes_power
N = no_power
A = abstain_power (существует только у моделей с вариантом ABSTAIN, §1.1.1)
V=Y+N+A (Сумма проголосовавших сил; для моделей без ABSTAIN — просто V=Y+N)
T = total_voting_power_at_creation (замороженная сумма сил участников на момент создания предложения; КОНСТАНТА для данного предложения, см. docs/01 §2.4). T НЕ пересчитывается при вступлении новых участников в процессе голосования данного предложения.
Qreq=T×(config.quorum_percentage/100) (Требуемый кворум)

## 1.4.1. Модель MAJORITY (Простое большинство)

Определение: Решение принимается, если "ЗА" проголосовало более 50% от общей силы организации (абсолютное большинство), игнорируя кворум.

PASSED: Если
Y > T/2.

REJECTED: Если
N ≥ T/2 ИЛИ истекло время (expires_at).
Логика: Кворум (quorum_percentage) в данной модели игнорируется. Неявившиеся автоматически считаются голосующими против. Поле quorum_percentage в config должно игнорироваться или устанавливаться в 0 при выборе этой модели.

Реализация (улучшение модуля): MajorityModel и QuorumModel используют ОБЩЕЕ ядро сравнения (общий базовый класс или хелпер). MAJORITY эквивалентна QUORUM с «виртуальным» счётчиком против N_eff = N + (T - V) и порогом 50%: тождество Y > N_eff ⟺ Y > T/2. При этом MAJORITY остаётся ОТДЕЛЬНОЙ стратегией в фабрике, поскольку имеет иные наблюдаемые поведения: статус EXPIRED невозможен никогда, условие раннего REJECTED — N ≥ T/2, неявка трактуется как ПРОТИВ.

## 1.4.2. Модель QUORUM_PERCENTAGE (Квалифицированное большинство)

Определение: Сначала проверяется, собрали ли мы нужную явку. Если явка есть, побеждает большинство проголосовавших.

PASSED: Если
V ≥ Qreq И Y > N.

REJECTED: Если
V ≥ Qreq И N ≥ Y.

EXPIRED (Не достигнут кворум): Если время истекло (expires_at < now) И V < Qreq.

Логика: Модель допускает ТОЛЬКО YES и NO (§1.1.1): явка V = Y + N; не сделавший vote не учитывается нигде — ни в кворуме, ни в соотношении. Попытка отдать ABSTAIN отвергается с -32005.

## 1.4.3. Модель CONSENT (Консент / Отсутствие возражений)

Определение: Решение принимается, если ни один участник не высказался "ПРОТИВ". Кворум здесь измеряется не в силе, а в количестве голов (участников).

PASSED: Если
N == 0 И voters_count>0. (Хотя бы один человек должен проголосовать "ЗА", и никто "ПРОТИВ").

REJECTED: Если
N > 0.

EXPIRED: Если время истекло и voters_count==0. Примечание: если по истечении времени voters_count>0, но все проголосовавшие воздержались (N==0 И Y==0), консенсус не достигнут (нет ни одного "ЗА") -> статус EXPIRED по аналогии.

## 1.5. Обработка краевых случаев (Edge Cases)

-Голосование с силой 0.0: Агент со статусом ACTIVE, но voting_power = 0.0 (при SHARES) имеет право голосовать. Его голос увеличивает voters_count, но не меняет значения
Y,N,A. Это важно для модели CONSENT.
-Замороженная T (неизменность во время голосования): T фиксируется при создании предложения (total_voting_power_at_creation) и НЕ меняется при вступлении новых участников в процессе голосования данного предложения. Новые участники влияют только на total_voting_power самой Организации (docs/01 §2.2) и, следовательно, на T будущих предложений. Это гарантирует детерминированность итогов голосования и упрощает Early-Exit оптимизацию (порог прохождения не "плывет" в процессе).
-Невозможный Консенсус (Early Exit Optimization): Движок C++ при каждом голосовании проверяет, возможен ли еще PASSED. Если нет — сразу закрывает предложение со статусом REJECTED. Общее условие невозможности PASSED: максимальный достижимый Y_max = Y + (T - V) (все еще не проголосовавшие голосуют "ЗА") не превышает порог модели:
MAJORITY: Y + (T - V) <= T/2.
QUORUM_PERCENTAGE: Y + (T - V) <= N, либо кворум недостижим в принципе (T < Qreq).
Корректный пример: T = 100, Qreq = 80, участники суммарной силой 60 голосуют "NO" (N = 60). Остаток силы равен 40, поэтому максимальный Y = 40 <= N = 60: PASSED недостижим ни при каком раскладе -> немедленный REJECTED.
Внимание: недостаточно проверять только N — например, при N = 30 и T = 100 PASSED всё еще возможен (оставшиеся 70 силы дают Y = 70 > N и V = 100 >= Qreq), поэтому раннее закрытие в этом случае было бы ошибкой.
