OpenSpec: Версионирование схемы и миграции (Schema Versioning & Migrations)
Версия: 1.0.0
Статус: Draft

# 1. Проблема

RocksDB не имеет понятия «ALTER TABLE». После релиза данные живут в JSON-строках (docs/01): при добавлении нового поля в доменную сущность (например, `delegate_vote` в Proposal) старые записи этого поля не содержат. Разбросанные по коду проверки `if (field_exists)` — хрупкое и уродливое решение, которое не масштабируется с числом версий.

# 2. Решение: глобальная версия схемы

- Константа `VOTERPOOL_SCHEMA_VERSION` компилируется в бинарник (текущая версия схемы кода).
- При СОЗДАНИИ новой БД движок записывает ключ `meta:schema_version` = VOTERPOOL_SCHEMA_VERSION (default CF; значение — целое число).
- При КАЖДОМ старте: открыть БД → прочитать `meta:schema_version`:
  - ключа нет и БД пустая → инициализация: записать текущую версию;
  - db_version < VOTERPOOL_SCHEMA_VERSION → выполнить цепочку миграций v → v+1 → … → текущая, затем обычный старт;
  - db_version == текущей → обычный старт;
  - db_version > текущей → ФАТАЛЬНО: данные новее бинарника (даунгрейд не поддерживается). `spdlog::critical` + exit(1) с понятным сообщением.

# 3. Устройство миграции

- Каждый шаг — функция `MigrateV{n}_To_V{n+1}(DB&)`: префикс-итератор по затронутым CF, преобразование JSON-записей, коммит пачками WriteBatch (рекомендуемый батч — 10 000 записей) с периодическим Flush.
- ИДЕМПОТЕНТНОСТЬ ОБЯЗАТЕЛЬНА: версия в `meta:schema_version` повышается только ПОСЛЕ успешного завершения шага. Падение посреди миграции → при рестарте шаг запускается заново и обязан корректно пропускать уже преобразованные записи (проверка наличия новых полей). Это даёт возобновляемость без отдельного чекпоинта.
- Правила написания шага:
  новые поля получают значения по умолчанию (`delegate_vote: ""`);
  переименование — запись нового поля + удаление старого;
  смена типа — двойная запись;
  НЕИЗВЕСТНЫЕ поля сохраняются: parse полного объекта → мутация → serialize (не пересобирать объект «с нуля»).
- Единая точка десериализации: кодеки доменных сущностей в слое repositories — единственное место, знающее схему. Бизнес-логика никогда не парсит JSON напрямую (docs/07 §1.4 — simdjson только на границе MCP).

# 4. Пример шага v1 → v2 (добавление delegate_vote)

Итератор cf_proposals → для каждой записи: parse → if (!has delegate_vote) set "" → batch.Put → каждые ~10k записей коммит → после прохода атомарный WriteBatch: meta:schema_version=2. Лог: "Migrating schema v1 → v2 … done (N records)"; метрика voterpool_schema_migration_records_total{from,to} (docs/11).

# 5. Взаимодействие с подсистемами

Порядок старта: открыть БД → проверить/выполнить миграции → ТОЛЬКО ЗАТЕМ поднимать TTL/SSE воркеры и HTTP-сервер (docs/04 §1.5.2).
Вторичные индексы: если миграция меняет поля, участвующие в индексах (tags, category, name, feed), шаг ОБЯЗАН переиндексировать затронутые ключи в тех же WriteBatch — то же правило, что для UPDATE_ORG_INFO (docs/01 §5 алгоритм).
Конфигурация не версионируется этим механизмом (config.yaml читается всегда актуальным бинарником).

# 6. Тестирование миграций

- Integration: фикстура «БД версии N» (записи генерируются кодеком старой версии прямо в тесте) → запуск движка → проверка: версия повысилась, все данные сохранены, дефолты проставлены, индексы согласованы (tests/integration/test_migration.cpp, docs/10 §2.2).
- Crash-тест: обрыв процесса посреди миграции → повторный старт дозавершает шаг (проверка идемпотентности).
- Gate-тест: БД с версией НОВЕЕ бинарника → процесс завершается с exit(1) до открытия сервера.
