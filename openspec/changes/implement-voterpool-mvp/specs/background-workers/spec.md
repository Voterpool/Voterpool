## Purpose

Фоновые процессы: закрытие просроченных предложений (TTL-воркер), асинхронная рассылка SSE-событий (диспетчер с очередью) и управление жизненным циклом — грациозное завершение по SIGTERM/SIGINT и фазы startup/recovery (docs/04).

## ADDED Requirements

### Requirement: TTL-воркер просроченных предложений

Фоновый процесс ДОЛЖЕН примерно раз в секунду находить активные предложения с истёкшим expires_at через отсортированный по времени вторичный индекс (prefix-scan с остановкой на первом неистёкшем ключе, без полного перебора). Для каждого найденного: удалить ключ индекса ПЕРВЫМ делом в транзакции закрытия (исключая повторную обработку после сбоя), вычислить финальный статус моделью консенсуса (PASSED/REJECTED/EXPIRED), применить последствия PASSED (config_delta/ACTION), поставить событие proposal_closed. Закрытие ДОЛЖНО захватывать тот же per-proposal замок, что и голосование.

#### Scenario: Закрытие просроченного предложения

- **WHEN** expires_at предложения наступил
- **THEN** в пределах секунды предложение получает итоговый статус по модели, ключ из индекса активности удалён, подписчики получают proposal_closed

#### Scenario: Нет повторной обработки после сбоя

- **WHEN** процесс падает между удалением ключа индекса и коммитом статуса, затем рестартует
- **THEN** предложение не закрывается второй раз; согласованность восстанавливается без дублей событий

#### Scenario: Неистёкшие предложения не трогаются

- **WHEN** скан выполняется при наличии и истёкших, и активных предложений
- **THEN** обрабатываются только истёкшие; скан останавливается на первом неистёкшем ключе

### Requirement: Асинхронный SSE-диспетчер

Доставка SSE-событий ДОЛЖНА выполняться отдельным фоновым потоком через конкурентную очередь: продюсеры (голосование, TTL, мутации) кладут события за O(1) и не блокируются на сетевом вводе-выводе; диспетчер читает очередь пачками до 1000 событий и передаёт записи в сетевые циклы безопасно (без прямой записи из фоновых потоков). При остановке диспетчер ОБЯЗАН выгрести оставшиеся события (drain).

#### Scenario: Продюсер не блокируется медленным клиентом

- **WHEN** голосование происходит, пока медленный SSE-клиент не читает поток
- **THEN** cast_vote отвечает штатно; события ставятся в очередь и доставляются/отбрасываются диспетчером независимо

#### Scenario: Drain при остановке

- **WHEN** получен сигнал остановки при непустой очереди событий
- **THEN** диспетчер доставляет оставшиеся события перед завершением

### Requirement: Грациозное завершение

По SIGTERM/SIGINT движок ДОЛЖЕН выполнить последовательность: прекратить принимать новые HTTP/MCP соединения → асинхронно закрыть все SSE-стримы кадром server_shutdown → запросить остановку воркеров (TTL завершает текущую итерацию; диспетчер дренирует очередь) → синхронно сбросить memtable хранилища на диск и корректно закрыть базу → сбросить буферы асинхронного логгера → завершиться с кодом 0.

#### Scenario: SIGTERM завершает с кодом 0

- **WHEN** работающему движку отправляется SIGTERM при активных SSE-подписках
- **THEN** клиенты получают кадр server_shutdown, данные сброшены на диск, процесс завершается кодом 0

#### Scenario: Повторные сигналы безопасны

- **WHEN** SIGTERM приходит во время уже идущей процедуры остановки
- **THEN** завершение остаётся корректным без повреждения данных

### Requirement: Фазы запуска и восстановления

При старте движок ДОЛЖЕН: открыть хранилище с проверкой WAL (автоматический replay после сбоя) → проверить/выполнить миграции схемы → только затем поднять воркеры и HTTP-сервер → начать отвечать 200 OK на GET /health. Опционально восстановить индекс активных предложений сканом предложений, если он повреждён.

#### Scenario: Холодный старт после сбоя

- **WHEN** процесс убит без грациозной остановки и запускается заново
- **THEN** незакоммиченные транзакции откатываются журналом, состояние консистентно, /health отвечает 200 после полного подъёма

#### Scenario: Миграции до старта сервера

- **WHEN** база имеет версию ниже текущей
- **THEN** миграции завершаются прежде, чем воркеры и HTTP начнут работу
