# Design — fix-spec-compliance-audit

## Context

Аудит подтвердил 5 дефектов (см. proposal.md). Ключевые факты текущего кода, определяющие решения:

- `OrgRepository::putMembership` пишет обратный индекс `cf_agent_orgs` только при `status == ACTIVE`; ключи членств в `cf_memberships` идут org-first, поэтому выборка «все орги агента» без индекса невозможна.
- `scanNameQuery` делает Seek по префиксу запроса — подстрока в середине имени лексикографически недостижима. Потребители имени-индекса: поиск (`SearchOrganizations.cpp`) и проверка дубликата в `CreateOrg.cpp` (полный скан `org_name:` с get организации на совпадение).
- `parseOrgConfig` заполняет недостающие поля дефолтами (MAJORITY/51/3600/EQUAL), затем `finalizeLocked` присваивает `org.config = *p.config_delta`. На диск конфиг всегда сериализуется всеми 4 полями, поэтому дефолты при чтении никогда не срабатывают для записей этого бинарника.
- `finalizeLocked` пишет Proposal батчем **до** веток эффектов и не модифицирует его после; флаги исхода существуют только в `ClosedInfo` (для события), карточка и метрика их игнорируют; инкремент `voterpool_actions_applied_total` стоит до проверок лимитов.
- В `AppContext::init` блок `rebuild_index_on_start` разыменовывает `proposals` до конструирования репозиториев.

Ограничения от стейкхолдера: целевое поведение без обратной совместимости и миграций; один change на всё; поиск — подход «full in-memory scan» (резидентный реестр имён).

## Goals / Non-Goals

**Goals:**

- Код удовлетворяет существующим спекам agent-identity (#1), discovery (#2), organizations (#3), consensus-engine/mcp-protocol (#4), background-workers (#5).
- Исход применения эффектов становится наблюдаемым и единым источником для карточки, события и метрики.
- Поиск по подстроке — 100% точность за счёт резидентного реестра имён; тот же реестр обслуживает проверку дубликата имени.

**Non-Goals:**

- Миграция/переинтерпретация старых записей предложений (у них флаги исхода читаются как false).
- Самоисцеление старых PENDING-членств, пропущенных в индексе до фикса (запись появится при следующей мутации членства).
- N-граммные/полнотекстовые индексы, нечёткий поиск.
- Изменение форматов событий SSE, контрактов ошибок, REST/MCP API (кроме значений признаков карточки).

## Decisions

### D1. Обратный индекс членств пишется при любом статусе (#1)

`putMembership` пишет `cf_agent_orgs` безусловно; значение ключа (`role/status`) остаётся информационным — истина подтягивается через `getMembership`, как сегодня. `deleteMembership` уже симметричен.

*Альтернатива:* отдельный PENDING-индекс или скан `cf_memberships` по агенту — отклонено: удвоение структур при том же коде записи либо полный скан CF (ключи org-first). Безусловная запись идемпотентна и не меняет схему ключей.

### D2. Резидентный реестр имён организаций (#2)

Новый компонент `OrgNameRegistry` (src/storage):

```
                    ┌──────────────────────────────┐
 startup ──────────▶│ load(): скан cf_organizations│  ACTIVE-only
                    └──────────┬───────────────────┘
                               ▼
   std::vector<Entry{org_id, name_lower}>          ◀─ substring scan
   std::unordered_map<org_id, index>               ◀─ O(1) rename/erase
   std::shared_mutex (readers: search; writers: mutations)
```

- **API**: `matchQuery(queryLowered) -> set<org_id>` (подстрока), `findActiveByName(nameLowered) -> optional<org_id>` (дубликат), `add/rename/erase`.
- **Мутации строго после успешного коммита**: CreateOrg → `add`; UPDATE_ORG_INFO PASSED (ветки `castVote` и `closeProposalByTimer` после `db->commit`) → `rename`; `dissolveOrganization` после коммита → `erase`. Реестр — производный кэш; источник истины — RocksDB; рассинхрон лечится рестартом (load при старте).
- **RocksDB-ключи `org_name:` выводятся из употребления**: `setName/removeName/scanNameQuery` удаляются вместе с вызовами (create, UPDATE_ORG_INFO, dissolve). Индексы тегов/категорий остаются в RocksDB без изменений.
- **Потоки**: поиск выполняется на HTTP-потоках, мутации — под org-локами движка; `shared_mutex` даёт параллельные чтения и эксклюзивные записи.

*Альтернативы:* bounded-scan RocksDB-индекса — отклонено стейкхолдером (точность ограничена maxScan); trigram-индекс — сложность не оправдана при ≤10⁴–10⁵ организаций (<1 МБ / единицы МБ памяти, скан ~0.1 мс).

### D3. config_delta: merge-then-validate (#3)

`parseOrgConfig(cfgJson, required)` получает третий параметр `const OrgConfig* base`:

- поле присутствует в JSON → берётся из JSON; отсутствует → наследуется из `base`;
- валидации (диапазоны, CONSENT+SHARES, duration > 0) прогоняются по смерженному итогу;
- `CreateProposal` передаёт `&orgOpt->config`; `CreateProposal` сохраняет **смерженный полный** конфиг в `p.config_delta`.

Благодаря этому `finalizeLocked` (присваивание целиком) остаётся корректным без изменений, а карточка отдаёт полный смерженный конфиг (сценарий дельты mcp-protocol). Дефолты внутри `Codec::orgConfigFromJson` сохраняются только для десериализации старых записей, где поля всегда полные. `CreateOrg` вызывает без базы — config там обязателен целиком.

*Альтернатива:* требовать все 4 поля в дельте — отклонено: ломает эргономику частичных обновлений (ACTION-payload в проекте частичный) и не следует из спеки («итоговой конфигурации»).

### D4. Исход применения хранится на Proposal (#4)

- `Proposal` += `bool config_delta_applied = false; bool action_applied = false;`
- Сериализация — всегда оба поля; десериализация: отсутствие поля → `false` (без деривационного fallback — решение стейкхолдера «только целевое поведение»).
- `finalizeLocked`: первичный `put(batch, p)` переносится в конец функции; ветки эффектов выставляют флаги прямо на `p` (и в `ClosedInfo` для события — значения из одних и тех же вычислений). Ранние выходы (не-PASSED, орг распущена/отсутствует) оставляют флаги false.
- Инкремент `voterpool_actions_applied_total` переносится в две точки фактического применения: успех APPROVE_MEMBER (после проверок лимитов) и успех UPDATE_ORG_INFO.
- `GetProposal`: `action_applied` = `action_applied ? toString(kind) : null`; `config_delta_applied` = сохранённое значение. Карточка и `proposal_closed` становятся согласованы по построению.

*Альтернатива:* деривация в get_proposal с учётом dissolved-статуса орга — отклонено: воспроизводит рассинхрон, лимитный кейс всё равно недетектируем без хранения.

### D5. Порядок инициализации AppContext (#5)

Репозитории (`agents/orgs/proposals/votes/indexes/audit`) конструируются сразу после schema-gate; блок `rebuild_index_on_start` переносится после их конструирования. Повторная вставка индекса идемпотентна (put того же ключа).

## Risks / Trade-offs

- [Рассинхрон реестра при пропущенной точке мутации] → единая точка входа API реестра; integration-тесты на create/rename/dissolve; самовосстановление load() при рестарте.
- [Гонки чтение/запись реестра] → `shared_mutex` внутри компонента; мутации только post-commit.
- [Скрытые потребители ключей `org_name:` (тесты/checkpoint)] → grep-аудит перед удалением; прогон полного набора тестов, правка фикстур в рамках задач.
- [Полный скан реестра O(N) на запрос] → принято осознанно: ~100 мкс при 10k организаций; при деградации масштаба — точка расширения (trigram) без изменения контракта поиска.
- [Изменение семантики метрики `voterpool_actions_applied_total`] → счётчик перестаёт завышаться; зафиксировать в docs/observability при синхронизации документации.
- [Перенос put(batch, p) в конец finalizeLocked] → все записи одного атомарного батча, порядок внутри батча на коммит-семантику не влияет; покрыто существующими tx-тестами cast_vote/ttl.

## Migration Plan

Развертывание = перезапуск бинарника: реестр имён строится из `cf_organizations`, флаги исхода у новых закрытий пишутся сразу. Откат = предыдущий бинарник (он игнорирует новые JSON-поля Proposal и восстанавливает прежнее поведение поиска). Миграции данных нет.

## Open Questions

Нет — три открытых вопроса аудита разрешены стейкхолдером (без совместимости; один change; full in-memory scan).
