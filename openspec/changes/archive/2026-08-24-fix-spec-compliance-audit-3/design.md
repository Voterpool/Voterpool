# Design: fix-spec-compliance-audit-3

## Context

Пять подтверждённых расхождений specs↔код (см. proposal.md). Ключевые факты о текущем состоянии:

- Текст плейбука живёт в двух местах: строковая константа `kPlaybookText` (`src/mcp/tools/Playbook.cpp`) и человеческая копия `docs/14-agent-playbook.md`; формулировка «ровно одно из» продублирована в требовании «Создание предложения» (`openspec/specs/consensus-engine/spec.md`), которое противоречит собственному сценарию «Стандартное предложение».
- Индекс категории уже строится при создании организации (`setCategory` в том же WriteBatch, ранний return при пустом значении), UPDATE_ORG_INFO уже умеет category end-to-end; отсутствует только парсинг аргумента.
- `AuditLogRepository::append` использует namespace-static `g_seq` c `% 1000`; ключ собирается в `Keys::auditKey`, seq не паддируется (`std::to_string`). Все вызовы `append` идут внутри батчей мутаций под proposal/org-локами; чтение истории — prefix-scan `audit:{org}:`.
- `rocksdb::Statistics` нигде не создаётся; каталог метрик — статическая таблица `kCatalog` в `src/core/Metrics.cpp`; `/metrics` рендерится из `MetricsRegistry::expose()`.
- `runCheckpointCommand` открывает исходную БД и вызывает `SchemaManager::run()` до `Checkpoint::CreateCheckpoint`; спека миграций на стороне восстановления уже разрешает («более новый бинарник накатит миграции на копию»).

## Goals / Non-Goals

**Goals:**

- Контракт «предложение = org_id + title (+ description), action/config_delta опциональны и взаимоисключающи» сформулирован одинаково в плейбуке, docs и спеке.
- Организация находится поиском по категории сразу после создания.
- Append-only журнала аудита стал формально железным: ни одна запись не перезаписывается коллизией ключа.
- Эксплуатация получает низкоуровневые цифры RocksDB (кэш, компакция, WAL) в /metrics.
- `checkpoint` — чистая фотография данных: источник логически не меняется.

**Non-Goals:**

- Ретроактивная миграция старых ключей аудита (старые записи читаются префиксным сканом как есть).
- Расширение UPDATE_ORG_INFO или схемы Codec (category уже сериализуется).
- Экспорт гистограмм/timers RocksDB (дорогой сбор, docs/11 требует низкой стоимости) и per-CF метрик (новый лейбл — расширение дисциплины кардинальности).
- Изменение семантики восстановления (restore по-прежнему может выполнять миграции).

## Decisions

### D1. Формулировка про action/config_delta — одна каноническая фраза в трёх местах

Канон: *«create_proposal {org_id, title, description}; optionally AT MOST ONE of: action {kind: APPROVE_MEMBER|UPDATE_ORG_INFO, payload} or config_delta {...} — neither is valid too (plain STANDARD proposal)»*. В kPlaybookText §7 PROPOSING, в docs/14 §про create_proposal и в первом предложении требования «Создание предложения». Дельта-сценарий «Плейбук описывает стандартное предложение как допустимое» пинит текст тестом на подстроку. Логика CreateProposal.cpp не меняется — она уже канон.

Альтернатива: править только плейбук, оставив спеку как есть — отклонено: требование консенсуса противоречит своему же сценарию, именно оно породило неверный плейбук.

### D2. category — опциональный строковый аргумент create_organization

Парсинг симметричен tags/max_agents: поле присутствует и не строка → -32602; иначе `org.category = значение`. Дальше существующий конвейер делает всё сам: `putOrg` + `setCategory` уже в одном WriteBatch (поиск видит категорию атомарно с созданием), ответ дополняется полем `category`, `get_organization` уже возвращает её. Фильтр поиска приводится к нижнему регистру через `Keys::nameLower` — индексация регистронезависима, отдельной нормализации не нужно.

Альтернативы: авто-вывод категории из тегов — магия, отклонено; оставить как есть (D11.1) — отклонено пользователем: холодный старт без категории ломает заявленный сценарий discovery.

### D3. Ключ аудита — вариант B: монотонный 64-битный seq + boot-соль, всё в экземпляре репозитория

Формат ключа: `audit:{org|_}:{ts_ms %020lld}:{salt %016llx}{seq %019lld}`

- `seq` — `std::atomic<std::int64_t>` без modulo, живёт в полях экземпляра `AuditLogRepository` (не namespace-static): внутри запуска процесса значения уникальны по построению.
- `salt` — 64-битное случайное число на экземпляр (`std::random_device` + смешивание с адресом/временем для платформ, где random_device детерминирован): после рестарта хвост ключа другой даже при совпадении ms и seq.
- Оба поля фиксированной ширины → лексикографический порядок ключей одного бута совпадает с порядком записи (чинит найденный при аудите дефект порядка: непаддированный `std::to_string(seq)` сортировал `0,1,10,100,…`).
- Ноль дополнительных операций БД на событие: один `fetch_add` (~нс) против варианта A (персистентный счётчик per-org: +1 Get на каждое событие и риск гонки вне локов) и варианта C (UUID-суффикс: вероятностная гарантия, теряется порядок внутри ms).
- Prefix-scan `listByOrg` не меняется; записи старого формата остаются читаемыми; плейсхолдер `_` для событий без организации сохраняется.

Чтобы «рестарт» был тестируемым, соль/счётчик — состояние экземпляра: тест создаёт второй `AuditLogRepository` над той же БД и воспроизводит коллизионные условия точно.

### D4. RocksDB Statistics: включить всегда, публиковать перед скрейпом

- `opts.statistics = rocksdb::CreateDBStatistics()` в `RocksDBWrapper::open()` — стоимость сбора тикеров пренебрежима (docs/11 требует низкой стоимости; detailed timers не включаем).
- Публикация pull-моделью: `RocksDBWrapper::publishStatisticsToRegistry()` читает выбранные тикеры (`stats->getTickerCount`) и кладёт гейджи в `MetricsRegistry`; вызывается обработчиком `/metrics` непосредственно перед `expose()` — значения всегда свежие, фонового воркера не нужно. Если БД закрыта — публикация пропускается (реестр отдаёт последние значения; семейства, единожды объявленные в каталоге, не исчезают).
- Состав (9 семейств, все gauge без лейблов, HELP из kCatalog); источник значения — тикер Statistics или свойство БД (`GetIntProperty`), в зависимости от того, где RocksDB 7.8 его отдаёт:

| Метрика | Источник |
|---|---|
| voterpool_rocksdb_block_cache_usage | свойство rocksdb.block-cache-usage |
| voterpool_rocksdb_block_cache_capacity | свойство rocksdb.block-cache-capacity |
| voterpool_rocksdb_block_cache_hits_total | тикер BLOCK_CACHE_HIT |
| voterpool_rocksdb_block_cache_misses_total | тикер BLOCK_CACHE_MISS |
| voterpool_rocksdb_estimate_pending_compaction_bytes | свойство rocksdb.estimate-pending-compaction-bytes |
| voterpool_rocksdb_wal_synced_total | тикер WAL_FILE_SYNCED |
| voterpool_rocksdb_flush_write_bytes_total | тикер FLUSH_WRITE_BYTES |
| voterpool_rocksdb_compaction_read_bytes_total | тикер COMPACT_READ_BYTES |
| voterpool_rocksdb_compaction_write_bytes_total | тикер COMPACT_WRITE_BYTES |

- Префикс `voterpool_rocksdb_*` выбран вместо документированного ранее `rocksdb_*`: единое пространство имён `voterpool_*` во всём каталоге и дисциплина кардинальности спеки описаны вокруг него; docs/11 §3 правится соответственно.

Альтернатива: следовать docs буква в букву (`rocksdb_*`) — отклонено: разрыв стиля каталога дороже устаревшей строки таблицы.

### D5. Checkpoint — чистый снимок: убрать SchemaManager::run() и гейт целиком

Новый поток `runCheckpointCommand`: load config → `db.open()` → отказ при `!DbHealth::healthy()` → `Checkpoint::CreateCheckpoint` → `close()`. Никаких чтений/записей версии схемы: снимок фиксирует «как есть сейчас», включая старую версию схемы; миграция — забота движка, восстанавливающегося из копии (спека это уже разрешает и требует сценария «Снимок старой схемы новым бинарником»).

Гейт `kFatalNewerSchema` удаляется вместе с run(): чистая семантика фотографии означает «снимаем всё, что открывается» — байт-копия полезна оператору и при даунгрейде бинарника, а понять версию снимка он сможет на восстановлении. Принимаемый побочный эффект: `close()` выполняет Flush — меняется физическая раскладка (memtable→SST), но не логическое содержимое; фиксируем это в docs/13 явно.

Альтернатива: сохранить отказ на базе новее бинарника — отклонено пользователем («сделаем именно снимок, то есть всё что есть сейчас»): частичная фотография — не фотография.

## Risks / Trade-offs

- [Ключ аудита вырос на ~35 байт] → Незначимо на фоне JSON-значения события (~200+ байт); префиксный скан не деградирует.
- [Внутри одной миллисекунды порядок записей разных бутов случаен (сортировка по соли)] → Гарантия хронологии ограничена одним бутом (зафиксировано в спеке); несколько событий в один ms от двух запусков — практически невозможная ситуация.
- [Statistics держит внутренние счётчики в памяти] → Единицы килобайт; опция включается всегда, отдельного конфига не вводим (YAGNI; при необходимости добавим позже).
- [checkpoint больше не отказывает на базе новее бинарника] → Снимок такой базы безопасен (байтовая копия); риск ложного ожидания оператора снимается явной строкой в docs/13.
- [Тест плейбука привязан к подстроке текста] → Пинируется именно каноническая фраза из design D1; текст статичен для версии бинарника (docs/05 §1.0), дрейф маловероятен.
- [Старые аудито-записи с короткими ключами соседствуют с новыми] → Читаются тем же prefix-scan; порядок между форматами внутри одного ms не гарантирован — приемлемо (исторические данные).

## Migration Plan

Миграция данных не требуется: изменения формата ключа аудита самосовместимы (префикс прежний), схема БД не меняется, версия схемы не повышается. Деплой — замена бинарника и рестарт. Откат — возврат предыдущего бинарника; записи нового формата остаются читаемыми старым кодом (prefix-scan). Единственное поведенческое изменение для операторов: checkpoint больше не модифицирует источник и не отказывает на схеме новее бинарника.

## Open Questions

Нет — три спорных решения (вариант B ключа, префикс метрик, чистый снимок без гейта) зафиксированы пользователем при выборе этого изменения.
