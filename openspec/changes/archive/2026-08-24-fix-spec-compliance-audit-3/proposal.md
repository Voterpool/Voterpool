# Fix spec compliance audit round 3

## Why

Третий раунд аудита specs↔код выявил 5 подтверждённых расхождений. Плейбук (инструмент get_playbook и docs/14) запрещает агентам создавать обычные STANDARD-предложения, хотя код и спека их разрешают; create_organization не принимает category, из-за чего новая организация невидима для поиска по категории до отдельного голосования (и docs/05 §1.2 при этом расходится с PRD docs/00); ключ аудита `audit:{org}:{ms}:{seq%1000}` со счётчиком в RAM допускает коллизии и молчаливую перезапись записей append-only журнала; rocksdb::Statistics, обещанная design и docs/11, не включается и не экспортируется; CLI-команда checkpoint перед снимком гоняет миграции на живой исходной базе, превращая «фотографию данных» в скрытый migrate.

## What Changes

- **Плейбук разрешает STANDARD**: текст get_playbook, docs/14-agent-playbook.md и формулировка требования «Создание предложения» в consensus-engine приводятся к контракту кода: org_id + title (+ description), action/config_delta опциональны, задавать оба одновременно нельзя (-32005).
- **category при создании организации**: create_organization принимает опциональный string-аргумент category; значение индексируется тем же механизмом category:, что и при UPDATE_ORG_INFO, поэтому поиск search_organizations {category} находит организацию сразу после создания.
- **Ключ аудита без коллизий**: seq перестаёт обнуляться по модулю 1000 и жить только в RAM: 64-битный монотонный счётчик экземпляра репозитория + zero-pad фиксированной ширины + случайная boot-соль процесса в хвосте ключа. Коллизии между событиями одного процесса невозможны (уникальный seq), между перезапусками — невозможны благодаря соли; хронологический порядок внутри одной миллисекунды обеспечивается паддингом.
- **RocksDB Statistics экспортируется**: rocksdb::Statistics включается при открытии БД; отобранный набор тикеров экспонируется в /metrics гейджами под префиксом voterpool_rocksdb_* без лейблов (docs/11 уточняется: префикс voterpool_rocksdb_ вместо rocksdb_).
- **Checkpoint — чистый снимок** (**BREAKING** для сценария «бэкап старой директории новым бинарником»): команда checkpoint больше не вызывает SchemaManager::run() — источник не мигрирует и не меняется логически; снимок фиксирует состояние «как есть сейчас», включая старую версию схемы; миграция выполняется движком, восстанавливающимся из копии. Гейт «схема новее бинарника» из команды убран: снимок семантически байт-копия и допустим для любой открывающейся базы.

### Modified Capabilities

- `consensus-engine`: требование «Создание предложения» переформулировано: action/config_delta — опциональные взаимоисключающие поля («не более одного из»); сценарий «Стандартное предложение» остаётся каноническим примером.
- `organizations`: требование «Создание организации» дополняется опциональным аргументом category с немедленной индексацией и видимостью в поиске по категории сразу после создания.
- `data-persistence`: требование «Неизменяемый журнал аудита» дополняется гарантией уникальности ключей записей (никакая запись не может быть перезаписана коллизией ключа) и точности хронологического порядка чтения; требование «Бэкапы через согласованные снапшоты» дополняется инвариантом чистого снимка: команда checkpoint НЕ выполняет миграций и логических мутаций исходной базы, версия схемы источника сохраняется.
- `observability`: требование «Каталог метрик Prometheus» дополняется семействами voterpool_rocksdb_* (фиксированный набор тикеров Statistics, гейджи без лейблов).

Примечание: правка плейбука (get_playbook/docs/14) приводит артефакт к уже зафиксированной в consensus-engine семантике создания предложения — кроме уточнения самой формулировки требования consensus-engine отдельной дельты для mcp-protocol не требуется (требование «Инструмент get_playbook» не пинит спорную фразу).

- **Docs**: docs/14-agent-playbook.md (§ про create_proposal), docs/05-mcp-contracts.md §1.2 (category в аргументах/ответе), docs/00-initial-prd.md:133 уже верен; docs/01-data-scheme.md (формат ключа cf_audit_log), docs/11-observability.md §3 (voterpool_rocksdb_* вместо rocksdb_), docs/13-backup-recovery.md (чистый снимок, миграция на стороне восстановления).
