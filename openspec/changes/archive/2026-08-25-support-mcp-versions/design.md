# Design: поддержка разных версий MCP

## Context

Сервер реализует собственный диалект MCP: stateless, без handshake, с обязательными заголовками маршрутизации `Mcp-Method`/`Mcp-Name` и жёстким равенством версии `2026-07-28` (docs/05 §1.0, спека mcp-protocol). Реальные клиентские SDK (opencode, Claude, Cursor — официальный `@modelcontextprotocol/sdk`) говорят по опубликованному streamable HTTP: присылают `initialize` со своей версией для переговоров, шлют notification `notifications/initialized`, не знают кастомных заголовков. Три гейта отсекают их до диспетчеризации (см. proposal.md — Why): версия, обязательные заголовки, отсутствие хендлера initialize.

Точки входа в код: `AuthMiddleware::handle` (`src/server/AuthMiddleware.cpp` — предварительные проверки), `mcp::handleMcpPost` (`src/mcp/McpHandler.cpp` — диспетчеризация), регистрация маршрутов (`src/server/VoterpoolApp.cpp` — `/mcp` только `{drogon::Post}`, сейчас GET/DELETE падают в 404 drogon).

## Goals / Non-Goals

**Goals:**

- Стандартный клиент подключается «из коробки» без единого кастомного заголовка и без ошибок на своей стороне: initialize → 202 → tools/list → tools/call.
- Существующие клиенты диалекта (заголовки, режим B, `_meta`-auth) работают без изменений.
- Stateless остаётся ядром: никаких сессий, любой инстанс за round-robin обрабатывает любой запрос.
- Версии сервера управляются конфигом, а не константой в middleware.

**Non-Goals:**

- SSE-потоковый ответ на POST /mcp (application/json разрешён спецификацией; SDK его принимает).
- Серверные уведомления через стандартный GET-stream `/mcp` (остаётся проприетарный `/mcp/events`).
- Поддержка HTTP+SSE транспорта редакции 2024-11-05.
- Изменение инструментов каталога, консенсуса, авторизации.

## Decisions

### D1. Заголовки — validate-if-present, без strict-флага

Отсутствие любого из `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name` перестаёт быть ошибкой; при наличии заголовок обязан согласовываться с телом (-32600 при расхождении). Значения для логов/метрик выводятся из уже разобранного тела (`probeBody` и так извлекает method; имя инструмента добавляется туда же).

*Альтернативы:* конфиг-тумблер `mcp.strict_headers` для enterprise-WAF — отклонён: добавляет второе состояние всей протокольной поверхности и матрицу тестов ×2, а выгоду (принуждение клиентов к диалекту) никто не запрашивал; WAF-маршрутизация по заголовкам работает и без принуждения. Отдельный режим «диалект-only» можно вернуть позже отдельным change'ом, если появится запрос.

### D2. Переговоры версии: эхо поддержанной, fallback на protocol_version

Источники версии по приоритету: заголовок → `params.protocolVersion` (стандартное место у initialize) → `_meta["io.modelcontextprotocol/protocolVersion"]`. Расхождение источников — -32600 c `data.supportedVersions` (сохраняем существующую семантику). Отсутствие версии во всех источниках — не ошибка (нечего сверять).

На initialize сервер возвращает запрошенную версию, если она входит в `supported_versions`; иначе — первый элемент списка (каноничный `2026-07-28`). На не-initialize запросах заявленная версия обязана входить в список (иначе -32600).

*Альтернативы:* всегда отвечать каноничной версией — отклонено: SDK разрывает соединение при получении незнакомой версии, что воспроизводит баг пользователя («ошибки на клиенте»); отвечать произвольной версией клиента без ограничений — отклонено: сервер тогда обещает совместимость с неизвестными будущими ревизиями, которые может не выдержать.

### D3. Список версий в конфиге, а не константа

`mcp.supported_versions: ["2026-07-28", "2025-06-18", "2025-03-26"]` в `config/default.yaml`, переопределение `VOTERPOOL_MCP_SUPPORTED_VERSIONS` (CSV). Валидация: непустой список непустых строк, обязан содержать `mcp.protocol_version` (он остаётся каноничной/предпочтительной версией и fallback'ом), иначе exit 1 — в духе существующей фатальной валидации конфига.

### D4. initialize и notifications — в McpHandler, до авторизационной логики

Ветка `method == "initialize"` рядом с `server/discover`/`tools/list`: анонимная, собирает `{protocolVersion, capabilities:{tools:{listChanged:false}}, serverInfo}` (serverInfo.name = "voterpool", version — существующая строка из discoverResponse). Ответ БЕЗ `Mcp-Session-Id` — клиент SDK после такого ответа живёт standalone, stateless сохраняется. Запросы без поля `id` (любые notifications) отвечаются `HTTP 202` с пустым телом сразу после парсинга тела, до диспетчеризации: JSON-RPC запрещает отвечать на notifications чем-либо, а текущая -32601 с телом ломает SDK.

*Альтернативы:* эмулировать сессию (выдавать id сессии, держать состояние) — отклонено: противоречит Shared-Nothing ядру docs/05; обрабатывать notifications как обычный метод — отклонено выше.

### D5. Явный 405 на GET/DELETE /mcp

Drogon отвечает 404 на незарегистрированные методы; SDK распознаёт 405 как «SSE-потока нет, работаем standalone». Регистрируются явные обработчики `{Get, Delete}` для `/mcp`, возвращающие 405 с `Allow: POST`. Это контрактное поведение (спека), а не надежда на дефолт фреймворка.

### D6. Порядок проверок в AuthMiddleware

Сохраняется существующее правило «неразборчивое тело не нарушает протокол»: если method из тела не извлечён — предварительные проверки пропускаются, запрос доходит до хендлера и получает -32700/400. Новое: проверки версии выполняются только когда версия реально заявлена; проверка согласованности заголовков — только когда заголовки есть. Логирование mwLog остаётся: -32600 теперь пишется только на реальные нарушения (расхождение источников/заголовков, неизвестная версия), а не на отсутствие заголовков.

## Risks / Trade-offs

- [Будущая ревизия MCP изменит форму tools/list или tools/call] → Список версий конфигурируем: проблемную версию оператор убирает одной строкой; клиенты получают честный -32600 с supportedVersions вместо тихой несовместимости.
- [Эхо версии создаёт впечатление полной поддержки ревизии] → В design и docs/05 фиксируется: совместимость заявлена на уровне транспортного ядра (JSON-RPC поверх POST + tools/*), расширения диалекта опциональны.
- [Клиенты, сегодня зависящие от -32600 на отсутствии заголовков] → Таких нет в репозитории: все e2e-фикстуры шлют заголовки добровольно и продолжат проходить ветку validate-if-present; регресс покрывается существующими тестами test_protocol/test_transport.
- [-32700 precedence] → Сохранён существующий контракт: битое тело доходит до хендлера независимо от заголовков; сценарий уже покрыт спекой ошибок.

## Migration Plan

Обратная совместимость полная: старые клиенты диалекта не меняют ни одного байта. Новый дефолтный конфиг добавляет `mcp.supported_versions`; существующие конфиги без ключа получают дефолтный список (ключ опционален, валидация применяется после подстановки дефолта). Rollback — откат бинарника; изменений схемы хранилища нет. После деплоя владелец VPS подключает opencode штатным `mcp.json` без прокси и заголовков.
