# Design: Fix Consensus Finalize Atomicity

## Context

`ConsensusEngine::finalizeLocked` (src/consensus/ConsensusEngine.cpp:71, 110, 150) пишет организацию через `OrgRepository::put(const Organization&)`, который внутри создаёт собственный WriteBatch и коммитит немедленно (OrgRepository.cpp:7-11). Статус предложения, индексы и аудит идут в батч вызывающего и коммитятся позже. Мотивация — см. proposal.md; требования атомарности уже зафиксированы в data-persistence и consensus-engine.

Проверено по коду: остальные составные мутации атомарны — тулзы используют `db_putOrg(app, batch, …)` (ToolHelpers.h:80), роспуск организации полностью батчевый. Исправляется последний обходной путь.

## Goals / Non-Goals

**Goals**
- Единый атомарный коммит для полного эффекта закрытия PASSED-предложения (proposal + индексы + аудит + организация).
- Переиспользование установленного паттерна batch-перегрузок репозитория.

**Non-Goals**
- Изменение семантики `finalizeLocked` (порядок применения эффектов, лимиты, идемпотентность пропусков).
- Транзакализация `AgentRepository::put` и одиночных записей (они самодостаточны).
- Отказоустойчивость на уровне двухфазного коммита между CF — RocksDB WriteBatch уже даёт атомарность.

## Decisions

### D1: Batch-перегрузка в самом репозитории

`bool put(rocksdb::WriteBatch& batch, const Organization& org)` — зеркало существующей пары `putMembership(batch, …)` / `putMembership(…)`. Реализация: `db_.put(batch, "cf_organizations", Keys::org(...), Codec::serializeOrg(org))` без коммита.

Альтернативы:
- *Использовать `db_putOrg` из mcp/tools/ToolHelpers.h* — консенсусный слой не должен зависеть от MCP-слоя; хелпер дублирует логику сериализации. Отклонено; опционально позже `db_putOrg` может делегировать новой перегрузке (не в scope этого изменения).
- *Вернуть из finalizeLocked список отложенных org-записей* — усложняет сигнатуру ради того же результата. Отклонено.

### D2: Порядок операций внутри батча не меняется

`finalizeLocked` мутирует in-memory копии (`orgOpt`, `updated`) и добавляет операции в батч; чтения организации происходят до записи (`d_.orgs->get` читает закоммиченное состояние). Внутри одного WriteBatch порядок применения линеен, конфликтов чтение-после-записи нет. Замена трёх вызовов `put` на batch-вариант не требует реордеринга.

### D3: Тестирование отказа через существующий шов

`RocksDBWrapper::beforeCommitHook` (RocksDBWrapper.h:69) уже используется тестами (`test_cast_vote_tx.cpp:50`, `test_degraded_mode.cpp:17`) — инжекция `return false` в `commit()`. Сценарий: голос, закрывающий APPROVE_MEMBER-предложение, при отклонённом коммите → ни один эффект не виден; снятие хука → следующее закрытие применяет эффект ровно один раз (регресс двойного инкремента `total_voting_power`).

## Risks / Trade-offs

- [Дублирование org-записи в батче при повторном finalize того же предложения] → невозможно: после успешного коммита статус терминален и повторный finalize не вызывается; при неуспешном — батч не применён целиком.
- [Увеличение размера единственного батча] → на величину одной org-записи; некритично.

## Migration Plan

Замена трёх вызовов + новая перегрузка; развёртывание обычное. Откат — revert. Существующие тесты `test_cast_vote_tx` должны пройти без правок (контракт коммита не меняется).
