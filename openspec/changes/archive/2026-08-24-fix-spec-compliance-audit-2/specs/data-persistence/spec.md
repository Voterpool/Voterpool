## MODIFIED Requirements

### Requirement: Идемпотентные возобновляемые миграции

Каждый шаг миграции ДОЛЖЕН быть идемпотентным: версия повышается только после успешного завершения шага; падение посреди миграции → рестарт дозавершает шаг, пропуская уже преобразованные записи. Новые поля ДОЛЖНЫ получать значения по умолчанию; неизвестные поля ДОЛЖНЫ сохраняться (полный parse-mutate-serialize). Если шаг затрагивает проиндексированные поля — переиндексация обязана идти теми же пакетами. Число преобразованных записей ДОЛЖНО учитываться метрикой миграций. Миграция ДОЛЖНА различать два случая записи: запись, являющаяся корректным JSON без новых полей (старый формат), ДОЛЖНА мигрировать штатно с сохранением всех остальных полей; запись, не являющаяся корректным JSON (битая), НЕДОПУСТИМА к исправлению: движок ДОЛЖЕН записать в лог критическое сообщение с ключом записи, прервать миграцию, НЕ повышая версию схемы и НЕ изменяя содержимое хранилища, и завершить процесс с кодом 1 до подъёма воркеров и HTTP. Восстановление после такого отказа выполняется оператором вручную (checkpoint/точечный разбор записи); после устранения записи следующий рестарт повторяет миграцию с нуля, не трогая уже преобразованные записи.

#### Scenario: Возобновление прерванной миграции

- **WHEN** процесс падает посреди миграции v1→v2 и перезапускается
- **THEN** шаг завершается заново без дублей и порчи данных; версия становится 2

#### Scenario: Сохранение неизвестных полей

- **WHEN** миграция преобразует записи, содержащие поля, которых нет в схеме текущей версии
- **THEN** эти поля сохраняются в значениях после миграции

#### Scenario: Старый формат мигрирует штатно

- **WHEN** в cf_proposals лежит корректный JSON предложения без config_at_creation и движок мигрирует v1→v2
- **THEN** запись получает поле config_at_creation со значениями по умолчанию, все прочие поля сохраняются, версия схемы повышается до 2

#### Scenario: Битая запись останавливает старт фатально

- **WHEN** в cf_proposals лежит значение, не являющееся корректным JSON, и движок мигрирует v1→v2
- **THEN** процесс завершается кодом 1 с критическим сообщением, содержащим ключ битой записи; версия схемы остаётся 1; содержимое хранилища не изменяется; HTTP и воркеры не поднимаются

#### Scenario: Рестарт после исправления битой записи

- **WHEN** оператор удалил/восстановил битую запись из checkpoint и перезапустил движок
- **THEN** миграция v1→v2 выполняется заново, уже преобразованные записи не изменяются повторно, сервер поднимается
