## Context

Этап 1 (change `add-shard-ready-ports`) смёржен: плоскости Directory/Identity/Event за портами, конфигурация cluster.mode существует. docs/16 v2.0.0 §3.2 фиксирует бакетную модель. См. proposal.md «Why».

## Goals / Non-Goals

**Goals:**
- Граница шарда в данных: непрерывный диапазон `b{NNN}:` на каждую организацию.
- Миграция по паттерну docs/12: автоматическая, идемпотентная, возобновляемая, с dry-run.
- Нулевое внешнее поведение: golden-fixture Этапа 1 остаётся зелёным.

**Non-Goals:**
- Распределение бакетов по узлам, карта bucket→node, гейтвей — Этап 3.
- Изменение сетевых контрактов, инструментов, форматов ответов.
- Ребалансировка и перенос живых организаций между узлами.

## Decisions

### D1. Хэш и K

`fnv1a64(org_id) mod 256`. FNV-1a 64: детерминирован, не зависит от endianness при каноничной байтовой последовательности, тривиален для тест-векторов, распределение для UUID-подобных org_id достаточно равномерное. Альтернативы: SHA-256 trunc — дороже без выгоды; cityhash/xxhash — зависимости/платформенные различия. K=256 фиксируется константой в конфиге (`cluster.buckets`, только чтение; изменение = новая миграция). Тест-векторы коммитятся в `tests/fixtures/bucket_vectors.json`.

### D2. Слоёность ключей

Keys.h сохраняет текущие сигнатуры функций-конструкторов; добавляется слой `ScopedKey(Keys::org(id)) → "b117:org:{id}"`. Все вызовы орг-plane конструкторов проходят через BucketResolver::scope(). Такой порядок минимизирует diff: точка вставки одна, а не каждый call-site. Системная плоскость вызывает Keys напрямую (без scope) — изоляция проверяется статическим тестом-инвентарём.

### D3. Миграция

Шаг SchemaVersion N→N+1 (docs/12): single pass по каждой CF, для ключа без префикса `b`: определить семейство → вычислить целевой префикс:
- `org:*` и вложенные — bucket из org_id ключа;
- `tag:/category:` — bucket из суффиксного org_id;
- `org_feed:*` — bucket из хвостового org_id;
- `audit:{org}:*`, `pending:{org}:*`, `join_limit:{org}:*` — bucket из org_id префикса;
- `active_proposals:*` — bucket через proposal_lookup→org (lookup мигрируется последним шагом и читается до его переноса);
- `agent_orgs:{agent}:{org}` — bucket из org_id.
Порядок: lookup и системные НЕ переносим; перенос батчами по 10k записей с checkpoint-маркером `meta:migration:N+1:last_key` → докат после падения без дублей (ключ-источник удаляется в том же WriteBatch, что запись приёмника). Dry-run режим (`--migrate-dry-run`): считает и пишет отчёт, не меняет данные. Инвентаризационный тест: список обрабатываемых префиксов генерируется из констант Keys.h — добавление нового keyspace ломает тест, пока миграция не обновлена.

### D4. Мульти-бакетные сканы

Пер-бакетная итерация: для scan-операций цикл i∈[0,K) с seek(`b{i:03d}:`+innerPrefix). Лента ACTIVE: результаты собираются в существующую сортировку по revTs — порядок неизменен (спека требует эквивалентности порядка). TTL-воркер: цикл по бакетам внутри одного тика; длительность скана вырастает кратно — замеряется бенчмарком (порог <10% фоновых операций; алгоритмическая страховка: seek мимо пустого бакета дёшев).

### D5. Стратегия тестирования

(1) Юнит: тест-векторы hash (границы 0/255), кросс-платформенный прогон в CI-матрице; ScopedKey форматирование. (2) Миграция: пустая база (no-op версия+1); населённая (счётчики и точечные чтения); идемпотентность повторного запуска; kill -9 посреди → докат (fixture базы + скрипт прерывания); инвентаризация keyspaces. (3) Эквивалентность: golden-fixture Этапа 1 на legacy и после миграции — deep-equal, включая next_cursor; отдельный сценарий «данные в бакетах 0/127/255». (4) Перф: TTL-воркер и search p99 до/после. Весь suite зелёный — обязательный критерий завершения.

## Risks / Trade-offs

- [Пропуск keyspace в миграции] → инвентаризационный тест D3 (падает на новых префиксах) + dry-run отчёт ревьюится перед боевой миграцией.
- [Неравномерность hash → горячий бакет] → FNV на UUID даёт ~равномерно; мониторинг: метрика записей на бакет добавляется в /metrics (voterpool_bucket_records{bucket}) — перекос виден заранее; перераспределение возможно только новой миграцией (осознанно).
- [Деградация TTL/search от 256 seeks] → порог в tasks; при превышении — merge-итератор по бакетам вместо последовательного цикла (локальная оптимизация без смены контрактов).
- [Миграция на большой базе блокирует старт] → батчи 10k + логирование прогресса; окно недоступности фиксируется в runbook docs/12 как плановое обслуживание.

## Migration Plan

Стандартный путь docs/12: остановить сервис → заменить бинарник → старт (авто-миграция с прогрессом) → health-check. Откат до записи новых данных: предыдущий бинарник отказывает на схеме новее (контракт docs/12) — откат = восстановление из checkpoint, сделанного перед апгрейдом (обязательный шаг runbook). После старта новых записей отката нет — только forward-fix. План соответствует SH-6 требованиям к процедуре.
