## Purpose

Логические бакеты (docs/16 §3.2, Этап 2 Стратегии 3): граница шарда зафиксирована в keyspace — каждая орг-принадлежащая запись хранится под префиксом `b{NNN}:`, где NNN детерминированно выведен из org_id. Одиночная нода владеет всеми бакетами по умолчанию; кластерный перенос бакета становится непрерывным диапазоном ключей. Контракт покрывает функцию размещения, формат ключей, миграцию схемы и полноту сканов.

## ADDED Requirements

### Requirement: Детерминированная функция размещения

Размещение организации ДОЛЖНО вычисляться чистой функцией `bucket(org_id) = fnv1a64(org_id) mod 256` (K=256). Функция ДОЛЖНА быть заморожена набором тест-векторов, включая граничные значения (бакеты 0 и 255), и обязана давать одинаковый результат на всех поддерживаемых платформах. Изменение алгоритма или K допустимо только новой миграцией схемы.

#### Scenario: Тест-векторы размещения

- **WHEN** BucketResolver вычисляется для фиксированного набора org_id из тест-векторов
- **THEN** результат совпадает с эталонными значениями, включая org_id с бакетом 0 и бакетом 255

#### Scenario: Кросс-платформенный детерминизм

- **WHEN** резолв выполняется на сборках x86_64 и arm64
- **THEN** результаты идентичны для всех векторов

### Requirement: Формат ключей с префиксом бакета

Каждая запись орг-принадлежащих семейств (`org:*`, `org:{id}:member/proposal/vote`, `audit:{org}:*`, `pending:{org}:*`, `join_limit:*`, `tag:*`, `category:*`, `org_feed:*`, `active_proposals:*`, `agent_orgs:*`) ДОЛЖНА храниться под префиксом `b{NNN}:` (три цифры, NNN = bucket(org_id)). Системная плоскость (`meta:*`, `auth:{hash}`, `agent:{id}`, `proposal_lookup:{pid}`) ДОЛЖНА оставаться без префикса. Запись `agent_orgs` размещается в бакете организации.

#### Scenario: Запись и чтение через префикс

- **WHEN** создаётся организация с известным bucket(org_id)=117 и в неё пишутся member/proposal/vote
- **THEN** все соответствующие ключи физически начинаются с `b117:` и читаются только по этому диапазону

#### Scenario: Системная плоскость без префикса

- **WHEN** выполняются register_agent и cast_vote (резолв proposal_lookup)
- **THEN** ключи `agent:{id}` и `proposal_lookup:{pid}` записаны без префикса бакета

### Requirement: Миграция схемы N→N+1 идемпотентна и возобновляема

Миграция ДОЛЖНА выполняться автоматически при старте бинарника новее базы (механизм docs/12), переписывая орг-ключи legacy-формата в префиксные. Повторный запуск на мигрированной базе ДОЛЖЕН быть no-op; прерванная миграция (падение процесса) ДОЛЖНА докатываться при следующем старте без потерь и дублей записей. Миграция ДОЛЖНА быть покрыта тестом инвентаризации: перечень обрабатываемых префиксов выводится из Keys.h и падает при появлении нового keyspace без обновления списка.

#### Scenario: Перенос населённой базы

- **WHEN** база с организациями, членствами, предложениями, голосами, аудитом, тегами и лентой стартует под новым бинарником
- **THEN** после миграции каждая запись доступна по новому ключу, счётчики записей до/после совпадают, legacy-ключи отсутствуют

#### Scenario: Идемпотентность

- **WHEN** миграция запускается повторно на уже мигрированной базе
- **THEN** изменений нет, версия схемы не меняется повторно, время выполнения пренебрежимо

#### Scenario: Возобновление после прерывания

- **WHEN** процесс убит посреди миграции и база открывается заново
- **THEN** докат завершается без дублей и потерь; финальное состояние идентично непрерывной миграции

### Requirement: Полнота мульти-бакетных сканов

Все операции, читающие каталог или индексы без указания организации (search_organizations, TTL-воркер active_proposals, listOrgsOfAgent), ДОЛЖНЫ обходить ВСЕ K бакетных префиксов. Отсутствие данных в части бакетов НЕ ДОЛЖНО влиять на результат.

#### Scenario: Данные в крайних бакетах находятся

- **WHEN** созданы организации, попавшие в бакеты 0, 127 и 255, и выполняется search_organizations / истечение их предложений / get_agent
- **THEN** результаты включают данные всех трёх бакетов без пропусков и дублей

#### Scenario: Эквивалентность порядка выдачи

- **WHEN** лента ACTIVE сравнивается между legacy-раскладкой и бакетной на одинаковом наборе организаций
- **THEN** порядок и состав элементов идентичны (сортировка ленты не зависит от разбивки по бакетам)

### Requirement: Одиночная нода владеет всеми бакетами по умолчанию

В режиме standalone (по умолчанию, без секции cluster) приложение ДОЛЖНО работать со всеми K=256 бакетами локально без какой-либо дополнительной конфигурации. Конфигурация cluster.mode остаётся ограниченной значением standalone (fail-fast на иных значениях сохраняется от Этапа 1); распределение бакетов по узлам в этот change не входит.

#### Scenario: Старт без конфигурации кластера

- **WHEN** свежий или мигрированный запуск без секции cluster
- **THEN** полный функционал доступен: создание/поиск организаций, голосование, SSE — без упоминания бакетов в конфигурации пользователя

### Requirement: Golden-эквивалентность до и после миграции

Полный инструментый канонический сценарий (register→create_org→join→create_proposal→cast_vote→закрытие→search→get_agent→SSE) ДОЛЖЕН давать идентичные ответы на legacy-раскладке и после миграции в бакетную, включая пагинацию поиска курсором.

#### Scenario: Регрессия форматов ответов

- **WHEN** golden-fixture из change Этапа 1 прогоняется на бакетной раскладке
- **THEN** ответы идентичны fixture (структуры, значения, коды ошибок, next_cursor)
