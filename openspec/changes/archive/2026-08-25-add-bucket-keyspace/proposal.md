## Why

docs/16 v2.0.0 (Этап 2, Стратегия 3): чтобы кластерное шардирование стало инфраструктурной операцией, граница шарда должна существовать В ДАННЫХ. Сейчас ключи консенсус-плоскости и каталога не несут признака владельца — перенос «половины организаций» между узлами невозможен без перебора всех записей. Префикс логического бакета `b{NNN}:` делает диапазон шарда непрерывным интервалом ключей: checkpoint/перенос/ребаланс становятся механикой, а placement новой организации — чистой функцией без состояния (закрытие SH-5).

## What Changes

- **BREAKING** Формат ключей RocksDB (внутренний, не сетевой): все орг-принадлежащие записи получают префикс бакета `b{NNN}:` — `org:*`, `org:{id}:member/proposal/vote`, `audit:*`, `pending:*`, `join_limit:*`, `tag:*`, `category:*`, `org_feed:*`, `active_proposals:*`, `agent_orgs:*`. Системная плоскость остаётся без префикса: `meta:*`, `auth:{hash}`, `agent:{id}`, `proposal_lookup:{pid}`.
- Автоматическая миграция схемы N→N+1 при старте по механизму docs/12: переименование существующих ключей с префиксом, restart-safe и идемпотентно (докатывается после прерывания).
- Заморозка функции размещения: `bucket(org_id) = fnv1a64(org_id) mod 256`; K=256; фиксация тест-векторами (границы 0 и 255 включительно). Алгоритм меняется только через новую миграцию.
- `BucketResolver` в scaling-слое (поверх портов Этапа 1): все конструкторы ключей орг-плоскости идут через него; мульти-бакетные сканы (лента поиска, TTL-воркер, listOrgsOfAgent) обходят все K префиксов.
- Конфигурация: секция `cluster.buckets: 256` (константа Этапа 2, изменение = новая миграция); mode по-прежнему только standalone — распределение бакетов по узлам НЕ входит в этот change (Этап 3).
- Документация: docs/01 (раскладка keyspaces v2), docs/12 (новая версия схемы и процедура), docs/16 §5 (стадия выполнена).

Внешнее поведение (MCP-инструменты, форматы, коды ошибок) не меняется — проверяется golden-регрессией из change Этапа 1.

## Capabilities

### New Capabilities

- `bucket-keyspace`: контракт логических бакетов — детерминизм и заморозка bucket(org_id), формат ключей орг-плоскости с префиксом `b{NNN}:`, неизменность системной плоскости, идемпотентность и возобновляемость миграции N→N+1, полнота мульти-бакетных сканов, дефолтная принадлежность всех K бакетов одиночной ноде.

### Modified Capabilities

_(нет — сетевые контракты не меняются; внутренняя раскладка описывается новой способностью)_

## Impact

- Код: `include/scaling/BucketResolver.h` + реализация; правки Keys.h (конструкторы принимают resolved-префикс либо обёртки); миграционный шаг в SchemaVersion runner; сканы ConsensusEngine.cpp (TTL), IndexRepository/OrgRepository/OrgNameRegistry (перевод на пер-бакетный обход); AppContext wiring.
- Предусловие: change `add-shard-ready-ports` смёржен (порты существуют; миграция не трогает портовые интерфейсы).
- Риски: (1) однократная миграция формата — купируется идемпотентностью, dry-run режимом и golden-эквивалентностью до/после; (2) ошибка hash-детерминизма между платформами — купируется тест-векторами; (3) оверхед 256-префиксных сканов — бенчмарк TTL-воркера и search до/после (порог <10% на фоновых операциях, <2% p99 запросов); (4) пропуск какого-либо keyspace при миграции — купируется тестом инвентаризации: список префиксов Keys.h vs список обработанных миграцией (тест падает при добавлении нового keyspace без обновления миграции).
