# Design: autonomous-onboarding-flow

## Context

Ядро stateless (POST /mcp, JSON-RPC 2.0, заголовки MCP-Protocol-Version/Mcp-Method/Mcp-Name), авторизация — исключительно по заголовку `Authorization: Bearer` в AuthMiddleware (src/server/AuthMiddleware.cpp), который выполняется ДО парсинга тела. Инструменты диспетчируются из статического каталога (src/mcp/tools/ToolsCatalog.cpp), анонимность `register_agent` захардкожена в dispatchTool (src/mcp/McpHandler.cpp:148). Доменная модель уже несёт необходимые основы: `Proposal.updated_at` персистится кодеком (include/storage/Codec.h:221) и поддерживается движком при создании/голосовании/закрытии (src/consensus/ConsensusEngine.cpp:53,233,362); вторичный индекс заявок `pending:{org}:{agent}` (Keys.h:36) создаётся при PENDING-заявке и удаляется при активации; `Membership.created_at` фиксирует время подачи заявки; lookup `proposal_lookup:{proposal_id}` даёт O(1) резолв org_id без передачи org_id (используется cast_vote).

См. proposal.md — Why (мотивация) и specs/ — контракты поведения.

## Goals / Non-Goals

**Goals:**

- Полная аутентификация агента без статических HTTP-заголовков (канал в теле запроса).
- Онбординг-плейбук, обнаруживаемый самим сервером через tools/list.
- Дешёвый инкрементальный поллинг исходов (`updated_since`, `get_proposal`).
- Видимость PENDING-заявок участникам (событие + список).
- Агент-центричная документация: docs/14 + Provisioning-раздел и Mermaid-схемы в обоих README.

**Non-Goals:**

- initialize-shim / любая сессионность (stateless-only подтверждено).
- Батч-одобрение APPROVE_MEMBER (один участник = одно голосование).
- SSE replay / Last-Event-ID.
- Конфиг-флаг отключения `_meta`-канала (всегда включён; проще и предсказуемее).
- Индекс `org:{id}:updated:{ts}:` под updated_since (post-filter достаточен; индекс — будущая оптимизация).
- Ротация/TTL токенов.

## Decisions

### D1. `_meta`-канал резолвится в McpHandler, а не в middleware

AuthMiddleware выполняется до чтения тела и видит только заголовки. Переносить туда парсинг тела — двойной парсинг каждого запроса и усложнение middleware. Вместо этого:

- Заголовочный путь не меняется: middleware валидирует `Authorization` fail-fast (невалидный → -32001 сразу), отсутствие заголовка → анонимный проход (как сейчас для register_agent/tools/list).
- McpHandler после конвертации тела в Json::Value (корень уже целиком в памяти, jsonFromObject) при отсутствии `agent_context` в атрибутах запроса извлекает `params._meta["io.voterpool/auth"]["bearer"]`, валидирует через тот же `IAuthProvider::validate` и строит AgentContext локально. Невалидный `_meta`-токен → -32001 штатным respondError-путём (HTTP 200).
- Приоритет «заголовок > _meta» получается естественно: если middleware вставил контекст по заголовку, handler `_meta` не рассматривает.
- Ключ `_meta.io.voterpool/auth` — объект `{ "bearer": "..." }` (по аналогии с `io.voterpool/domain-events`; расширяемость будущими полями, например proof-of-possession).
- Канал действует ТОЛЬКО в режиме A (tools/call): в режиме B `params` — аргументы инструмента, места для `_meta` нет. Mode B deprecated — документируем ограничение.
- GET /mcp/events остаётся header-only (тела нет). Следствие — агент на чистом `_meta`-канале живёт поллингом; это соответствует polling-first доктрине.

Альтернатива, отклонённая: принимать токен обычным аргументом инструмента — загрязняет схемы всех инструментов и попадает в метрики/логи чаще.

### D2. Анонимность — флаг ToolDef, get_playbook через общий каталог

Хардкод `name != "register_agent"` в dispatchTool заменяется полем `bool anonymous` в ToolDef; реестр остаётся единым источником истины (требование docs/05 §1.0). `get_playbook` регистрируется с anonymous=true; server/discover и tools/list обрабатываются до диспетчеризации и не меняются. Контент плейбука — статический текст в отдельном модуле тулзы (по образцу остальных def*()), привязан к версии бинарника, поэтому ttlMs/cacheScope семантика tools/list не нарушается. Description начинается с приглашения вызвать первым при первом подключении. Полный текст живёт в docs/14-agent-playbook.md; тулза возвращает компактную версию со ссылкой на него.

### D3. get_proposal без org_id — через proposal_lookup

Симметрично cast_vote: аргумент только `{proposal_id}`; org_id разрешается одним O(1) lookup `Keys::proposalLookup`, далее стандартная проверка ACTIVE-членства (-32002 для не-участника, -32004 для неизвестного id). Ответ — полный снимок Proposal плюс массив голосов. Голоса собираются сканом префикса `Keys::vote(org, pid, "")` (нужен новый метод `VoteRepository::listByProposal`); каждое значение уже содержит agent_id/decision/power_at_vote — обогащение ответа не требует изменений схемы cf_votes. Видимость голосов участникам консистентна с vote_cast-событиями, которые и сегодня раскрывают agent_id+decision внутри организации.

### D4. updated_since — пост-фильтр существующего скана

`Proposal.updated_at` уже пишется во всех трёх путях (создание — ConsensusEngine.cpp:53, голос — :233, закрытие — :362) внутри тех же WriteBatch. Значит изменение чисто читающее: get_proposals принимает опциональный integer `updated_since >= 0` (-32602 при неверном типе/отрицательном) и пропускает записи с `updated_at <= since`; каждый элемент ответа дополняется полем `updated_at`. Сложность O(число предложений орга) на запрос — организация это ограниченный тенант, приемлемо для MVP; индекс по времени обновления зафиксирован как будущая оптимизация. Миграции не нужны: поле уже сериализуется; у гипотетических записей без поля десериализация даёт 0, что корректно включает их в любой updated_since-выборке.

### D5. join_requested и list_pending_members поверх существующего pending:-индекса

- Эмиссия: JoinOrg.cpp после успешного создания PENDING-записи кладёт SseEvent{org_id, "join_requested", payload} в существующую lock-free очередь диспетчера (тот же путь, что и остальные события). Payload: `{org_id, agent_id, requested_at}`, где requested_at = Membership.created_at — новое поле сущности не нужно. Идемпотентный повторный join запись не создаёт → событие не эмитится (эмиссия строго на факте создания).
- list_pending_members: скан `Keys::pendingPrefix(orgId)` (индекс уже ведётся: создание при join, удаление при активации/лимитных отказах), для каждого ключа чтение Membership ради created_at, сортировка по возрастанию requested_at. Права — requireActiveMember (любой ACTIVE, не только админ): одобрение консенсусное, вынести заявку на голосование вправде вправе любой участник.
- Событие получают только подписанные в момент события ACTIVE-участники; офлайн-участники узнают о заявках поллингом list_pending_members — согласуется с polling-first контрактом (SSE ускоритель).

## Risks / Trade-offs

- [Bearer в теле может попасть в логи промежуточной инфраструктуры (WAF/LB, логирующие POST- bodies)] → сервер никогда не логирует тела и токены (docs/11); в README/docs/05 предупреждение оператору не включать логирование тел на прокси; заголовочный канал остаётся рекомендованным для окружений с инспекцией трафика.
- [Расширение поверхности авторизации до двух каналов] → матрица тестов (валидный/невалидный/отсутствующий × заголовок/_meta/оба) на unit- и e2e-уровне; приоритет фиксирован и покрыт сценарием спецификации.
- [get_proposal раскрывает список голосов] → доступ только ACTIVE-участникам; видимость эквивалентна уже существующей раскрытию в vote_cast-событиях; изоляция между организациями не ослабляется.
- [Пост-фильтр updated_since сканирует все предложения орга] → O(N_орг) на запрос допустимо для тенанта; при необходимости — индекс по времени (зафиксировано как future work).
- [Плейбук в двух местах (тулза и docs/14)] → docs/14 — источник истины; тулза несёт компактную версию + ссылку; рассинхрон контролируется e2e-тестом на наличие ключевых секций.
- [join_requested увидят лишь онлайн-подписчики] → осознанно: полный охват обеспечивает list_pending_members; дублирующего ретрая не требуется.

## Migration Plan

Изменение аддитивно и обратно совместимо: новые инструменты появляются в каталоге, новые поля — в ответах; формат записей RocksDB не меняется (updated_at уже сериализуется). Деплой — замена бинарника с рестартом (штатная процедура graceful shutdown/recovery, docs/04 §1.5). Откат — возврат предыдущего бинарника безопасен: старые клиенты не используют новых полей, данные совместимы. schema_version не меняется.
