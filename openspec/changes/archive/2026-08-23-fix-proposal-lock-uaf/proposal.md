# Fix Proposal Lock Use-After-Free

## Why

`ProposalLockRegistry` содержит опасный use-after-free: `Guard` хранит сырой указатель на `std::mutex`, а запись реестра остаётся единственным strong-владельцем мьютекса сразу после возврата `acquire()` (локальный `shared_ptr` разрушается при выходе). Все три пути закрытия предложения (`castVote`, `closeProposalByTimer`, `expireAllForDissolve`) вызывают `forget()` **до** разрушения Guard — мьютекс удаляется под замком, и деструктор Guard выполняет `unlock()` по освобождённой памяти. Это не редкая гонка, а детерминированный UB на каждом закрытии (голосовом, таймерном, при роспуске); конкурентность лишь расширяет окно (ждущий поток висит в `lock()` на удалённом объекте). Участок — горячий путь голосования, прямо затронут требованием сериализации из `data-persistence`.

## What Changes

- `ProposalLockRegistry::Guard` переходит на владение `std::shared_ptr<std::mutex>`: `forget()` стирает ссылку реестра, физическое удаление мьютекса откладывается до последнего `unlock()`. API (`acquire`/`forget`) не меняется.
- Фиксируется инвариант корректности (комментарий в заголовке + примечание в docs): `forget()` вызывается только после коммита терминального статуса предложения, а состояние перепроверяется внутри критической секции — это делает безопасным краткое перекрытие «старый держатель / новый держатель» после перевыпуска мьютекса.
- Документация: примечание в docs/04-background-workers.md о времени жизни записи реестра блокировок.
- Тесты:
  - unit-тест реестра: `forget()` при живом Guard не разрушает мьютекс до выхода Guard;
  - интеграционный тест гонки `cast_vote` vs `closeProposalByTimer` по одному предложению (ровно одно закрытие, опоздавший голос получает -32003);
  - прогон существующих e2e-сценариев закрытия предложений под ASAN-пресетом (heap-use-after-free должен быть устранён).
