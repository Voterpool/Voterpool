# Design: Fix Proposal Lock Use-After-Free

## Context

`include/consensus/ProposalLock.h`: `acquire()` копирует `shared_ptr<std::mutex>` в локальную переменную, но `Guard` сохраняет лишь сырой указатель; при возврате локальный `shared_ptr` разрушается и запись карты остаётся единственным владельцем. Все пути закрытия (`ConsensusEngine.cpp:266, 298, 313, 365`) вызывают `forget()` до разрушения Guard → мьютекс удаляется под замком. Реестр используется только `ConsensusEngine`; внешних потребителей нет.

## Goals / Non-Goals

**Goals**
- Устранить use-after-free при любом соотношении `acquire`/`forget`, сохранив API реестра.
- Зафиксировать инвариант, делающий безопасным перевыпуск мьютекса после `forget`.

**Non-Goals**
- Изменение гранулярности блокировок (остаётся один замок на proposal_id).
- Введение таймаутов/try-lock на пути голосования.
- Переработка стратегии конкурентности (требования зафиксированы в data-persistence).

## Decisions

### D1: Guard владеет shared_ptr

```cpp
class Guard {
    std::shared_ptr<std::mutex> m_;
public:
    explicit Guard(std::shared_ptr<std::mutex> m) : m_(std::move(m)) { if (m_) m_->lock(); }
    ~Guard() { if (m_) m_->unlock(); }
    // move-only, как сейчас
};
```

`acquire()` возвращает `Guard(entry)`, передавая копию `shared_ptr`. `forget()` стирает запись карты — физическое удаление откладывается до последнего unlock. Деструктор всегда разблокирует валидный объект.

Альтернативы:
- *Никогда не забывать записи* — неограниченный рост карты за время жизни процесса (предложений становится много); отклонено.
- *Координировать erase с деструктором Guard* (отложенная очередь очистки) — решает ту же задачу со значительной сложностью; отклонено.
- *Хранить weak_ptr в карте* + `lock()` при acquire — даёт автоматическую сборку пустых записей, но усложняет `forget`-семантику без пользы здесь: записи удаляются явно по терминальному статусу. Отклонено как преждевременное.

### D2: Инвариант «перевыпуск безопасен» фиксируется документацией

После `forget()` новый `acquire()` того же id создаёт **новый** экземпляр мьютекса: краткое окно, где старый держатель и новый acquirer одновременно находятся «в критических секциях» разных объектов. Это безопасно при двух условиях, которые выполняются и фиксируются комментарием в заголовке:
1. `forget()` вызывается строго после коммита терминального статуса предложения;
2. внутри критической секции состояние перепроверяется из БД (`castVote` читает свежий `p.status` после acquire) — опоздавший избиратель видит PASSED/EXPIRED и получает -32003.

## Risks / Trade-offs

- [Нарушение инварианта D2 будущим кодом] → комментарий-контракт в ProposalLock.h + примечание в docs/04; тест гонки закрепляет наблюдаемое поведение.
- [Дополнительное выделение shared_ptr-контроля на каждый acquire] → hot path голосования; накладные расходы атомарного refcount пренебрежимы на фоне RocksDB-коммита.

## Migration Plan

Изменение локально в одном заголовке; развёртывание = обычная замена бинарника. Откат — revert коммита. Проверка: полный e2e-набор под ASAN-пресетом (существующие сценарии закрытия предложений ранее должны были ловить heap-use-after-free).
