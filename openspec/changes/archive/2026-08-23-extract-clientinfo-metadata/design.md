# Design: Extract ClientInfo Metadata

## Context

`McpHandler::handleMcpPost` уже парсит тело в `Json::Value root` и замеряет длительность (`t0`); все пути обработки проходят через `recordRequestMetrics(method, name, ok)` — готовая единая точка. `AuthMiddleware` имеет свои два пути отказа (rejectProtocol, -32001). Логирование сегодня: только startup/shutdown/ошибки инструментов. Требования — observability «Структурированное логирование запросов» и «Каталог метрик», mcp-protocol «Метаданные клиента _meta»; кардинальность лейблов ограничена отдельным требованием (agent_id/org_id/proposal_id и произвольные строки запрещены).

## Goals / Non-Goals

**Goals**
- Одна структурная лог-запись на каждый POST /mcp (обработанный или отклонённый middleware) со всеми полями требования.
- Извлечение clientInfo в лог + ограниченный счётчик присутствия.
- Ноль риска кардинальности: client name/version только в тексте лога, не в лейблах.

**Non-Goals**
- Возврат request_id клиенту (заголовок X-Request-Id) — не требуется спекой; зарезервировано на будущее.
- Асинхронная лог-очередь — docs/08 уже описывает spdlog async; используем существующий логгер как есть.
- Логирование GET /mcp/events и /health — требование сформулировано для POST /mcp.
- Изменение форматов существующих метрик.

## Decisions

### D1: Единая точка — расширение recordRequestMetrics

Все ветки handler'а уже вызывают `recordRequestMetrics`; сигнатура расширяется до принятия контекста (durationMs, agentId, clientInfo, errCode) и эмитирует одну строку через spdlog::info. Это исключает рассинхрон «метрика есть — лога нет». Порядок полей фиксирован ключ=значение для grep-абельности:
`request_id=<id> agent_id=<id|-> method=<m> tool=<n> outcome=<ok|error> error_code=<code|-> duration_ms=<ms> client=<name|-> client_version=<v|->`

Альтернатива (лог на каждом return вручную) отклонена: 8+ путей выхода, неизбежные пропуски.

### D2: request_id без зависимостей

`std::atomic<uint64_t>` счётчик + pid процесса, hex-упаковка: `req-<pid:x>-<counter:x>`. Уникален в пределах процесса, монотонен, дёшев; корреляция между рестартами не требуется сценарием. CryptoUtil/UUID не привлекаются — генерация вызывается на каждый запрос.

### D3: Санитизация clientInfo перед логом

Значения name/version: обрезка до 64 символов, удаление символов < 0x20 и 0x7f (однострочность записи), пустая строка → прочерк. Реализовано чистой функцией `sanitizeLogValue(std::string)` — покрывается unit-тестами напрямую.

### D4: Отклонения middleware

В rejectProtocol и unauthorized-пути добавляется та же структура записи (request_id, outcome=error, error_code, причина), duration от момента входа middleware. Тело запроса и токены никогда не включаются. Счётчик client_meta в middleware НЕ инкрементируется (тело может быть не распарсено; семантика счётчика — «дошедшие до диспетчеризации»).

### D5: Метрика присутствия вместо лейблов клиента

`voterpool_mcp_client_meta_total{present=true|false}` инкрементируется раз на обработанный запрос. Лейбл из ограниченного множества — дисциплина кардинальности соблюдена; имя клиента осталось бы неограниченным.

## Risks / Trade-offs

- [Объём info-логов под нагрузкой] → одна строка на запрос согласована с docs/11; при необходимости глушится уровнем логирования (spdlog level), поведение метрик не меняется.
- [Двойное чтение _meta] → тело уже распарсено в root, извлечение O(1) по готовому дереву.
- [request_id не глобально уникален] → сценарии требуют корреляции внутри процесса; компромисс зафиксирован.

## Migration Plan

Обычная замена бинарника; обратной совместимости логов никто не гарантирует. Откат — revert.
