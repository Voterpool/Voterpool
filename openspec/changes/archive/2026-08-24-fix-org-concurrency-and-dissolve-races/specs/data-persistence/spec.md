## ADDED Requirements

### Requirement: Сериализация мутаций организации

Составные мутации состояния организации — активация вступления (проверка max_agents и joins_per_day_limit + запись членства + инкремент дневного счётчика + пересчёт total_voting_power), выход участника, передача прав администратора, изменение силы голоса, создание предложения (чтение замороженных T/H), роспуск (закрытие предложений + смена статуса + чистка индексов) и применение эффектов PASSED-предложения (config_delta, ACTION) — ДОЛЖНЫ выполняться критических секциях, сериализованных по идентификатору организации. Две конкурентные мутации одной организации НЕ ДОЛЖНЫ терять обновления (last-write-wins по устаревшей копии записи ЗАПРЕЩЁН): итоговое total_voting_power ДОЛЖНО равняться сумме сил ACTIVE участников после применения всех завершённых операций, а число фактических активаций НЕ ДОЛЖНО превышать установленные лимиты. Порядок блокировок ДОЛЖЕН быть единым (сначала блокировка предложения, затем блокировка организации) и исключать взаимные тупики; держатель блокировки организации НЕ ДОЛЖЕН ожидать блокировок предложений. Одновременное голосование за разные предложения одной организации ДОЛЖНО оставаться параллельным.

#### Scenario: Конкурентные вступления при лимите 1

- **WHEN** два агента одновременно вызывают join_organization для OPEN-организации с joins_per_day_limit = 1 и свободным max_agents
- **THEN** ровно одна операция возвращает ACTIVE, вторая получает -32005; дневной счётчик вступлений равен 1, total_voting_power увеличен ровно на одну силу

#### Scenario: Ноль потерянных обновлений total_voting_power

- **WHEN** N операций (вступления, выходы, update_voting_power) выполняются concurrently над одной организацией
- **THEN** после их завершения total_voting_power равен сумме voting_power всех ACTIVE участников; ни один инкремент/декремент не потерян

#### Scenario: Гонка смены силы с лимитом 100%

- **WHEN** ADMIN параллельно выполняет две операции update_voting_power, каждая из которых по отдельности укладывается в 100%, а вместе превышают
- **THEN** не более одной операции успешно применена; сумма сил участников не превышает 100% (+допуск на погрешность); отклонённая операция получает -32005 с attempted_sum

## MODIFIED Requirements

### Requirement: Конкурентный контроль per-proposal

Все операции чтение-модификация-запись над предложением (cast_vote, закрытие по таймеру и закрытие при роспуске организации) ДОЛЖНЫ сериализоваться по proposal_id; операции над РАЗНЫМИ предложениями ДОЛЖНЫ выполняться параллельно. Потерянные обновления счётчиков ЗАПРЕЩЕНЫ; ровно один агент = один голос; ровно одно закрытие предложения при гонке голоса и таймера. Блокировка предложения ДОЛЖНА удерживаться до завершения коммита записи с терминальным статусом; удаление записи блокировки ДОЛЖНО выполняться только после успешного коммита терминального статуса. Внутри критической секции состояние предложения И статус его организации ДОЛЖНЫ перепроверяться из хранилища: голос в распущенную организацию ДОЛЖЕН отклоняться (-32004), голос в уже закрытое предложение — -32003. Порядок блокировки ДОЛЖЕН исключать взаимные тупики (не более одного proposal-замока и одного org-замка на операцию, порядок proposal → организация).

#### Scenario: Ноль потерянных обновлений

- **WHEN** N потоков одновременно голосуют по одному предложению разными решениями
- **THEN** финальные yes/no/abstain_power точно равны суммам принятых голосов, каждый агент учтён один раз

#### Scenario: Гонка cast_vote против закрытия по таймеру

- **WHEN** истекает expires_at в момент, когда агент отправляет голос
- **THEN** операции сериализуются: предложение закрывается ровно один раз, итоговый статус корректен для модели, двойного применения последствий нет

#### Scenario: Гонка cast_vote с роспуском организации

- **WHEN** агент отправляет голос в момент выполнения dissolve_organization для той же организации
- **THEN** операции сериализуются: либо голос полностью зафиксирован до закрытия предложения роспуском (и учтён в итоговых счётчиках EXPIRED-записи), либо отклонён ошибкой -32003/-32004; предложение остаётся закрытым ровно один раз, resurrection ACTIVE после DISSOLVED невозможна

#### Scenario: Эффекты PASSED-предложения не переживают роспуск

- **WHEN** предложение достигает консенсуса одновременно с роспуском организации, и роспуск фиксируется раньше
- **THEN** предложение закрывается со своим консенсусным статусом, но config_delta и ACTION (активация участника, правка метаданных) НЕ применяются к распущенной организации
