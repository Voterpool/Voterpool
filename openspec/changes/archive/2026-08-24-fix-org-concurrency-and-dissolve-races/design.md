## Context

См. proposal.md — Why. Текущее состояние:

- Сериализация голосований обеспечивается `ProposalLockRegistry` (include/consensus/ProposalLock.h) с задокументированным контрактом: forget — только после успешного коммита терминального статуса; внутри критической секции состояние перепроверяется из хранилища. Контракт нарушает только путь роспуска (`expireAllForDissolve` вызывает forget до коммита батча, который делает вызывающий код в DissolveOrg.cpp).
- Все мутации записи Organization (join/leave/transfer_admin/update_voting_power/finalizeLocked) выполняют read-modify-write без синхронизации по организации; HTTP-слой Drogon многопоточный (`setThreadNum`), поэтому гонки реальны.
- Тестовая база: integration-тесты собирают полный `AppContext` через Harness и дёргают инструменты напрямую (`dispatchToolForTests`), есть паттерны конкурентных тестов на std::barrier (tests/integration/test_concurrency.cpp).

## Goals / Non-Goals

**Goals:**

- Восстановить контракт per-proposal лока на пути dissolve (Guard живёт до коммита, forget после коммита).
- Гарантировать отсутствие потерянных обновлений total_voting_power / счётчиков лимитов при конкурентных мутациях одной организации.
- Исключить взаимные тупики при сочетании proposal- и org-локов (явная иерархия).
- Сохранить параллелизм: разные предложения и разные организации мутируются независимо.
- Регрессионные тесты на обе гонки; все существующие тесты остаются зелёными.

**Non-Goals:**

- Переработка модели конкурентности Drogon (IO-пулы, шардинг по org_id).
- Замена WriteBatch-атомарности на транзакции/merge-операторы RocksDB.
- Изменение внешних контрактов MCP (коды ошибок, схемы событий) — поведение уточняется только в гонках.
- Оптимизация производительности горячих путей чтения (get_*/search_* остаются lock-free).

## Decisions

### D1. Единый keyed-mutex примитив для proposal и organization

`ProposalLockRegistry` обобщается в `KeyedMutexRegistry` (та же семантика acquire/forget/Guard, shared_ptr-мьютексы), с обратным алиасом `using ProposalLockRegistry = KeyedMutexRegistry;`. В `AppContext` добавляется второй экземпляр `orgLocks` (ключ — org_id).

*Альтернативы:* глобальный мьютекс на все мутации — убивает параллелизм разных организаций (противоречит data-persistence и NFR-3 Shared-Nothing); RW-лок на организацию — не нужен: читатели (get/search/profile) и так lock-free поверх атомарных чтений RocksDB, а писатели действительно эксклюзивны; merge-оператор RocksDB для счётчиков — подходит только для слепых инкрементов, но total_voting_power/max_agents/join_limit участвуют в check-then-act (лимиты, капа 100%), что без лока принципиально гоночно.

### D2. Иерархия локов: proposal → organization; держатель org-лока никогда не ждёт proposal-лок

Правила:

1. Операция держит не более одного proposal-лока и не более одного org-лока.
2. Если нужны оба — сначала proposal, затем organization (этот порядок используют castVote/closeProposalByTimer в ветвях применения эффектов PASSED).
3. Держатель org-лока НЕ выполняет блокирующих acquire proposal-локов (иначе возможен цикл с пунктом 2: dissolve(O→P) против finalize(P→O)).

Кто какие локи берёт:

| Операция | Локи |
|---|---|
| cast_vote | P; опционально O внутри finalize-ветвей (эффекты PASSED) |
| closeProposalByTimer | P; опционально O внутри finalize-ветвей |
| join_organization (OPEN) | O |
| leave_organization / transfer_admin / update_voting_power | O |
| create_proposal | O (статус + согласованный снимок T/H + вставка) |
| dissolve_organization | набор P (фаза 1), затем O (фаза 2); под O новых P-локов НЕ берёт |

### D3. Реструктуризация dissolve: движок владеет локами и коммитом

Вместо `expireAllForDissolve(batch, orgId)` (батч строит тулза, коммит снаружи) вводится `ConsensusEngine::dissolveOrganization(orgId)` → `{closedCount, events}` или ошибка хранилища. Алгоритм:

1. Список ACTIVE-предложений организации (без локов).
2. Фаза 1: собрать и удерживать Guard'ы по всем кандидатам, acquire в отсортированном по proposal_id порядке (два параллельных dissolve одной организации запрашивают локи в одинаковом глобальном порядке — цикл исключён; предложения разных организаций непересекающиеся).
3. Фаза 2: взять org-лок; перечитать кандидатов; один WriteBatch: EXPIRED + removeActiveIndex для всё ещё ACTIVE, Organization.status=DISSOLVED, чистка feed/name/tags/category, аудит ORG_DISSOLDED.
4. Коммит; при успехе — forget() каждого закрытого proposal_id (контракт восстановлен: forget строго после успешного коммита терминального статуса); снять org-лок, выпустить Guard'ы.
5. Зачистка «отставших»: предложения, созданные между шагами 1 и 3 и успевшие закоммититься до захвата org-лока, остаются ACTIVE-но-инертными (голосование/создание отклоняются проверкой статуса организации из D4); сразу после снятия локов выполняется ограниченный цикл повторов шагов 1–4 без барьера (только P-фаза), а естественным backstop'ом служит существующий TTL-воркер (предложение остаётся в активном индексе и будет закрыто EXPIRED по expires_at).

Тулза dissolve_organization сохраняет за собой авторизацию, SSE-доставку событий, метрики и refreshOrgGauges.

*Альтернатива:* собирать новые Guard'ы под org-локом для «отставших» прямо в барьере — отвергнуто: это O→P ожидание, создающее теоретический цикл с finalize(P→O) (созданное в окне предложение мгновенно достигает консенсуса). Отказ от O→P гарантирует отсутствие тупиков структурно, а не вероятностно.
*Альтернатива:* двухфазный коммит «барьер статуса, затем закрытие предложений отдельными батчами» — отвергнута: ломает требование organizations об атомарной чистке индексов вместе со сменой статуса и усложняет восстановление после сбоя между фазами.

### D4. Проверка статуса организации внутри критической секции голосования

`castVote`: после захвата proposal-лока и перечитывания предложения дополнительно читать статус организации; DISSOLVED → -32004 (быстрые проверки до лока остаются как fast-path). В `finalizeLocked` ветви применения эффектов (config_delta, APPROVE_MEMBER, UPDATE_ORG_INFO) оборачиваются в org-лок; если организация уже DISSOLVED — эффекты пропускаются (configDeltaApplied/actionApplied = false), предложение фиксирует консенсусный статус. Закрытие по таймеру статус организации не отклоняет — закрытие EXPIRED при роспуске и есть желаемый исход.

### D5. Обёртывание мутаций организации в org-лок

Критическая секция «чтение организации → проверки лимитов/ролей → сборка батча → commit» целиком берёт org-лок в: JoinOrg.cpp (OPEN-ветка), UpdateVotingPower.cpp, OrgGovernance.cpp (leave + transfer_admin), CreateProposal.cpp. PENDING-ветка join остаётся без лока: пишет независимые ключи, повторная запись тем же агентом идемпотентна (тот же ключ/значение). `IndexRepository::incrementJoinLimit` не меняется — оба его вызывателя (OPEN-join, APPROVE_MEMBER) теперь держат org-лок.

*Альтернатива:* блокировать весь вызов инструмента включая SSE/метрики — отвергнуто: критическая секция должна заканчиваться коммитом; доставка событий вне секции (уже так в castVote).

## Risks / Trade-offs

- [Мульти-Guard секция dissolve задерживает голосования по этим предложениям] → Редкая админская операция; кандидатов обычно единицы; Guard'ы держатся только на время сборки+коммита одного батча.
- [Кратковременное состояние «ACTIVE, но инертное» у отставших предложений] → Окно между списком и захватом org-лока — микросекунды; все взаимодействия отклоняются проверкой из D4; немедленная зачистка + TTL-backstop; сценарий явно описан в дельте organizations/data-persistence.
- [Пропущенный вызыватель мутаций организации → гонка сохраняется] → Аудит всех вызователей `db_putOrg`/`putMembership`/`incrementJoinLimit` в задачах; контракт фиксируется комментарием у `db_putOrg`; конкурентные тесты покрывают join×join, join×leave, power×power, vote×dissolve.
- [Тесты не могут детерминированно воспроизвести интерливинг] → Паттерн std::barrier + инвариантные утверждения (точные суммы/счётчики, ровно-K успехов) в N итерациях, как в существующих тестах Concurrency.
- [Регрессия тупиков при будущих правках] → Иерархия D2 документируется в docs/01 §5.3; правило «под org-локом нет ожидания proposal-лока» проверяется код-ревью чеклистом в tasks.md.
