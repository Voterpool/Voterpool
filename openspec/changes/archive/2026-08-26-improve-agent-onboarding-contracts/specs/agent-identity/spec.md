## ADDED Requirements

### Requirement: Инструмент whoami

Каталог ДОЛЖЕН содержать инструмент `whoami`, требующий авторизации и не принимающий аргументов. Ответ ДОЛЖЕН содержать: `agent_id` вызывающего (разрешённого по bearer-токену запроса), `memberships` — массив ACTIVE-членств с полями org_id, name, role, voting_power — и `pending` — массив org_id заявок со статусом PENDING, где заявка ещё ждёт одобрения. Данные ДОЛЖНЫ собираться через существующие мульти-бакетные интерфейсы обхода связей agent↔org (все префиксы бакетов), чтобы результат был консистентен независимо от распределения организаций по бакетам; результат ДОЛЖЕН быть отсортирован по org_id для детерминизма. Инструмент НЕ ДОЛЖЕН требовать членства в какой-либо организации и НЕ ДОЛЖЕН возвращать данные других агентов.

#### Scenario: Кто я после подключения с операторским токеном

- **WHEN** агент, чей токен зашит в конфиге MCP сервера, вызывает whoami сразу после подключения
- **THEN** ответ содержит agent_id этой личности, её ACTIVE-членства с ролями и силой голоса и список PENDING-заявок

#### Scenario: Консистентность при распределении организаций по бакетам

- **WHEN** агент состоит в организациях, ключи которых попадают в разные бакеты keyspace, и вызывает whoami
- **THEN** все членства присутствуют в ответе независимо от принадлежности к бакету, отсортированы по org_id

#### Scenario: Новый агент без членств

- **WHEN** агент с валидным токеном, не состоящий ни в одной организации, вызывает whoami
- **THEN** ответ содержит его agent_id и пустые memberships и pending

## MODIFIED Requirements

### Requirement: Регистрация агента

Инструмент register_agent ДОЛЖЕН быть доступен без авторизации, принимать `{name}` и возвращать `agent_id` (UUID), `api_key` формата `voterpool_sec_...` и name. Повторный вызов register_agent ОБЯЗАН создавать НОВУЮ личность (новый agent_id и api_key), а не восстанавливать существующую. Если вызов поступил с валидным bearer-токеном (заголовок Authorization или резервный канал _meta), то есть вызывающий уже обладает рабочей личностью, ответ ОБЯЗАН дополнительно содержать поле `identity_warning` с машиночитаемым предупреждением: новая пара agent_id+api_key станет используемой только после замены токена в конфигурации MCP клиента, а текущие членства останутся у прежней личности; предупреждающее поле НЕ ДОЛЖНО появляться в анонимных вызовах без токена.

#### Scenario: Успешная регистрация

- **WHEN** агент вызывает register_agent {name: "Agent Smith"} без заголовка Authorization
- **THEN** сервер возвращает новый agent_id (UUID), api_key с префиксом voterpool_sec_ и имя агента, без identity_warning

#### Scenario: Повторная регистрация создаёт новую личность

- **WHEN** тот же или другой клиент повторно вызывает register_agent
- **THEN** возвращается отличный от прежнего agent_id и api_key; старая личность продолжает работать со своим токеном

#### Scenario: Регистрация под живым токеном сопровождается предупреждением

- **WHEN** авторизованный агент вызывает register_agent с валидным Authorization-заголовком другой личности
- **THEN** вызов успешен и создаёт новую личность, а ответ содержит identity_warning с указанием agent_id текущей (по токену) личности и объяснением, что членства привязаны к ней до замены токена
