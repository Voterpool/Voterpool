## Why

Полевой прогон сервиса кодинг-агентом через 3 MCP-конфига выявил системные проблемы онбординга: агент не может ответить на вопрос «кто я и где я» (`get_agent` отражает только профиль), ошибки валидации плоские и не помогают исправить вызов, схемы инструментов не описывают поля (структуру `action.payload` невозможно открыть без ошибок), а ожидание исхода голосования требует polling+sleep. Сервис предназначен для агентов — контракт должен быть самоочевидным, точным и тестируемым на мульти-агентных сценариях.

Решение по итогам обсуждения (решения оператора):
- `_meta.io.voterpool/auth.bearer` остаётся внутренним резервным каналом, НЕ выносится в плейбук; единственная операторская идентичность агента — токен в конфиге MCP.
- Энумы остаются UPPERCASE и case-sensitive; факт case-sensitivity явно документируется.
- Long-poll `wait_proposal_close` вместо протокольных уведомлений; чистый SSE (/mcp/events) уже существует и не меняется.
- Список ожидающих вступления в CLOSED-организацию уже реализован и специфицирован (`list_pending_members`, organizations) — добавляется только подсветка в плейбуке и тесты.

## What Changes

- Новый инструмент `whoami`: `{agent_id, memberships[], pending[]}` одним вызовом; переиспользует мульти-бакетный скан `listOrgsOfAgent`.
- `register_agent` возвращает предупреждение `identity_warning`, когда вызов пришёл с валидным чужим bearer-токеном (создание второй личности при живой первой).
- Agent-friendly contracts:
  - каждый параметр каждой входной схемы получает `description`; ключевые инструменты получают `examples`;
  - строгая валидация аргументов: неизвестное поле или неверный тип → `-32602` с `data.hint` и ближайшей подсказкой (did-you-mean); тихое игнорирование полей устраняется;
  - типизированная схема `action` для `create_proposal` (kind enum + `payload.target_agent_id` / поля UPDATE_ORG_INFO);
  - карточки `get_organization` и `get_proposal` дополняются полем `allowed_decisions` из модели консенсуса;
  - ошибки бизнеса (-32002/-32003/-32005) обогащаются машинно-читаемыми подсказками в `data`.
- Новый инструмент `wait_proposal_close {proposal_id, timeout_sec?}` — long-poll до терминального статуса предложения или таймаута; ответ несёт финальный статус и агрегаты.
- Плейбук v2 (короткая версия в `get_playbook` + полный `docs/14-agent-playbook.md`): концентрированные блоки с точными JSON-шаблонами вызовов, формулировки MUST/MUSTN'T (MUST call whoami после connect; MUSTN'T re-register при -32001; MUSTN'T передавать org-поля в create_proposal; MUST учитывать case-sensitive энумы; must-порядок triage токена).
- E2E мульти-агентная матрица: 3 независимых токена, полный жизненный цикл (OPEN/CLOSED, все 3 модели консенсуса, APPROVE_MEMBER, UPDATE_ORG_INFO, config_delta), конфликтные и граничные случаи, включая identity-trap сценарий из полевого отчёта.

Не входит в объём: изменения SSE-эндпоинта, изменения формата существующих событий, изменение регистров энумов (совместимость), серверные сессии/_meta-auth продвижение.

### Modified Capabilities

- `agent-identity`: добавляются требования к инструменту `whoami` (мульти-бакетная консистентность member/pending-данных) и к предупреждению `register_agent` при живом стороннем идентити; уточняется требование просмотра профиля.
- `mcp-protocol`: добавляются требования — описания параметров во всех входных схемах tools/list, строгий контракт аргументов (-32602 + hint, запрет тихого игнорирования), типизированная схема action, long-poll инструмент `wait_proposal_close`, поле `allowed_decisions` в карточках, обновлённый контракт `get_playbook` (точность, MUST/MUSTN'T, JSON-шаблоны, case-sensitivity энумов).
