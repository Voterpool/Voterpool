## Context

Сервис работает как stateless MCP over HTTP (C++/drogon/RocksDB). Ключевые факты, определяющие дизайн:

- Авторизация запроса резолвится до диспетчеризации инструмента (`AuthMiddleware` → атрибут `agent_context`, плюс резервный канал `_meta.io.voterpool/auth.bearer` в `McpHandler`). Из этого следует, что внутри handler'а инструмента `tc.agent != nullptr` эквивалентно «вызов пришёл с валидным токеном» — предупреждение `register_agent` можно сделать одной локальной проверкой без изменения middleware.
- Связи agent↔org хранятся в бакете каждой организации (`cf_agent_orgs`, docs/16 §3.2); готовый мульти-бакетный обход — `OrgRepository::listOrgsOfAgent` (орг-id asc), возвращает членства всех статусов, включая PENDING. Отдельные pending-индексы (`pending:{org}`) нужны только org-стороне (`list_pending_members`); agent-стороне хватает фильтра статуса.
- Каталог инструментов статичен на версию бинарника (`ToolsCatalog`, кэшируемый tools/list) — ревизия схем безопасна для кэша.
- Консенсусные модели дают `allowedDecisions()`; точки фиксации терминального статуса предложения в коде сосредоточены: `ConsensusEngine::castVote` (досрочное), `closeProposalByTimer` (TTL и зачистка stale-индекса), `dissolveOrganization` (обе фазы). Все они уже держат proposal-lock и коммитят единым батчем.
- Handler'ы инструментов синхронны (`Result<Json::Value>`), исполняются на пути HTTP-callback — долгие блокировки в IO-потоке недопустимы.
- Мотивация и решения оператора — см. proposal.md; контракты — см. дельты specs/agent-identity и specs/mcp-protocol.

## Goals / Non-Goals

**Goals:**

- Один вызов самоидентификации агента (`whoami`) без новых индексов и миграций данных.
- Самоописывающие схемы и диагностируемые ошибки: агент исправляет вызов за один round-trip.
- Синхронная доставка исхода голосования (`wait_proposal_close`) через любой MCP-клиент.
- Плейбук как нормативный контракт (MUST/MUST NOT) с дословно воспроизводимыми JSON.
- Полная e2e-матрица мульти-агентных сценариев, включая воспроизведение каждого пункта полевого отчёта.

**Non-Goals:**

- Продвижение `_meta`-авторизации в публичный контракт; изменение SSE (`/mcp/events`) и формата событий; сессии/statefulness; изменение регистров энумов или их нормализация; история голосов в списке get_proposals; server push.

## Decisions

### D1. whoami поверх существующего мульти-бакетного интерфейса

Реализация одним обращением к `identity->listOrgsOfAgent(agent_id)` с разделением результата на ACTIVE (`memberships`, с name из `orgs->get`) и PENDING (`pending`). Альтернатива — отдельный глобальный agent-side индекс вне бакетов: отвергнута как дублирующая состояние (риск рассинхронизации) ради экономии одного прохода по ≤N префиксам, которые код и обязан обходить в любом случае (инвариант задокументирован в Keys.h и покрыт инвентаризационным тестом test_keys_bucket).

### D2. Предупреждение register_agent — на уровне handler'а

Проверка `tc.agent != nullptr` внутри `RegisterAgent`: анонимный путь не меняется; авторизованный получает то же тело ответа + `identity_warning` (структурированный объект: `current_agent_id`, текст причины). Альтернативы: отклонять вызов (-32005) — отвергнуто, регистрация легитимна (например, оператор заводит вторую личность заранее); отдельный заголовок-warning — нет, предупреждение обязано быть в теле того же ответа.

### D3. Строгая валидация: один общий gate + усиленные точечные проверки

Новый хелпер в `ToolHelpers`: каждый ToolDef получает декларативный список `allowedArgs` (имена + ожидаемый примитив типа), gate перед handler'ом:

- unknown key → `-32602` c `data.field` и did-you-mean (Левенштейн ≤ 2 либо общий префикс ≥ 4 символов среди известных имён инструмента);
- тип не соответствует объявленному в самой схеме каталога (те же структуры, что уходят в tools/list — единый источник правды) → `-32602` c ожидаемым типом;
- отсутствие required → существующее сообщение (сохраняем формулировки тестов).

Вложенность: `config`/`config_delta`/`action.payload` проходят тот же принцип внутри своих парсеров (неизвестный ключ внутри config → `-32602` + hint). Escape-hatch для развёртывания: конфиг-флаг `mcp.strict_arguments` (default true) — мгновенный откат поведения без релиза.

Альтернатива — встраивание полноценного JSON-Schema validator'а: отвергнуто (тяжесть зависимости, дублирование схем типов) — маленький декларативный gate покрывает 100% потребности и сам выводит hints.

### D4. Типизированная схема action и описания полей

Расширение helpers схем (`schemaString(desc)`, объектные конструкторы принимают description/examples) вместо введения DSL: ревизия всех 18 определений остаётся механической. `action` становится oneof-подобной структурой в рамках JSON-Schema draft, совместимой с клиентами harness'ов: properties kind (enum) + payload c target_agent_id/description-полями; examples добавляются трём сложным инструментам. Кэш tools/list инвалидируется сам (статичен на бинарник).

### D5. allowed_decisions в карточках

`get_organization` дописывает `allowed_decisions` из модели её конфига; `get_proposal` — из `config_at_creation`. Вычисление на лету фабрикой моделей (без хранения в записи): значение всегда консистентно с фактическим поведением cast_vote, включая error.data.allowed (единый источник — allowedDecisions).

### D6. wait_proposal_close: регистр подписчиков + вынос диспетчеризации в пул

- Новый `ProposalWaitRegistry` (server-layer, seam-интерфейс как SseHub для масштабирования): `map<proposal_id, std::vector<Waiter>>`, у Waiter — `std::condition_variable`/flag и deadline. Регистрация под общим мьютексом с double-check статуса после постановки в очередь (защита от lost wakeup).
- Notify во всех четырёх точках фиксации терминала (после успешного commit, до `locks->forget`): `finalizeLocked` пути из castVote и closeProposalByTimer, dissolve (барьерная фаза + sweeps), устраняя утечку ожидающих.
- Алгоритм вызова: resolve proposal → requireActiveMember (тот же -32002 без ожидания) → статус терминален? мгновенный ответ : register waiter → re-check → cv_wait_until(deadline) → перечитать карточку (proposals->get) и вернуть агрегаты+флаги; closed=false при таймауте.
- Исполнение: диспетчеризация **всех** tools/call переносится из IO-потока в небольшой worker-пул (размер в конфиге; ответ через захваченный drogon callback). Это единственный неблокирующий способ реализовать long-poll в текущей синхронной сигнатуре handler'ов; попутно снимает риск задержек любых медленных инструментов. Параллелизм ожиданий ограничен размером пула (per-config), деградация при исчерпании — обычная очередь, дедлайн гарантирует освобождение слота.
- Границы таймаута зафиксированы спекой ([1;90], default из конфига `mcp.wait_close_default_timeout_sec` = 30); max ниже типовых proxy-таймаутов (120s).

Альтернативы: протокольные server-notifications (зависимость от поддержки harness'ом, сложнее верифицировать) и активный sleep-poll внутри handler'а (нагрузка на чтение, те же требования к потокам) — отвергнуты.

### D7. Плейбук v2 как артефакт с тестовой защитой

Единственный источник короткой версии — `kPlaybookText`; полный гайд docs/14 переписывается тем же набором секций (расширение, не пересказ). Точность шаблонов защищается тестом: все JSON-блоки плейбука извлекаются и валидируются (имена инструментов существуют; argument keys ⊆ allowedArgs; enum-значения UPPER_CASE) против живого каталога — расхождение文档а и кода становится падающим тестом, а не полевым багом. `_meta`-канал и SSE сознательно исключены из текста (решение оператора), SAS-listing "что использовать / что НЕ использовать" формулируется RFC2119-стилем.

### D8. E2E-матрица как регрессия полевого отчёта

Один новый файл `tests/e2e/test_multi_agent_http.cpp` (3 агента через Harness/HttpUtil, реальные токены, переиспользование fixtures/bucket_vectors.json для принудительного распределения организаций по разным бакетам) + точечные расширения существующих e2e. Каждый пункт отчёта превращён в сценарий (identity-trap, payload APPROVE_MEMBER, UPDATE_ORG_INFO применение, filter=ALL у не-админа, поиск по имени, консистентность EXPIRED-карточек) — если регрессия когда-либо вернётся, матрица падает осмысленным сценарием.

## Risks / Trade-offs

- [Ужесточение валидации может сломать существующих клиентов с лишними полями] → флаг `mcp.strict_arguments` для мгновенного отката; базовые golden/e2e сценарии прогоняются до и после включения; решение задокументировано в release notes.
- [Long-poll истощает пул при массовом ожидании] → ограничение сверху временем (≤90s) и размером пула; очередь честная (FIFO); мониторинг через существующие метрики длительности tools/call + новый gauge активных ожидающих.
- [Notify-реестр — новое состояние в памяти] → потеря состояния при рестарте означает лишь возврат к немедленной проверке статуса (correctness не зависит от реестра; рестарт отрабатывает как таймаут-minimum); конкурентные writer'ы сериализуются proposal-lock'ом до notify.
- [Описания схем увеличивают payload tools/list] → рост ~десятки KiB; кэш server-side сохраняется, ttlMs механизм не меняется.
- [Блокирующий пул меняет модель исполнения диспетчера] → изменения локальны в McpHandler (одна точка вызова dispatchTool), всё остальное окружение нетронуто; интеграционный тест test_concurrency расширяется случаем N параллельных wait.

## Migration Plan

1. Добавление схемы/hint/whoami/wait/register-warning — аддитивно, деплой без остановки (stateless-сервер, single binary).
2. Включение строгой валидации под флагом на staging со снятыми метриками `-32602` по инструментам; затем прод и отключение возможности отката переключателем.
3. Rollback: обратный деплой бинарника безопасен (нет изменений схемы хранения и записей DB).
