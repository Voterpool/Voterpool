# Design: add-rps-benchmarks

## Context

Существующий `tests/bench/hot_path_bench.cpp` меряет только задержку (p50/p99, нс) однопоточного инпроцессного диспетчера. docs/10 §3.3 и карта покрытия обещают таргет `voterpool_bench` для пропускной способности (NFR-1) — его нет. Мотивация снятия численной планки и границы изменения — в proposal.md.

Технические факты, определяющие дизайн:

- Синхронная запись подтверждена в коде: `RocksDBWrapper.cpp` использует `wo.sync = true` на мутациях → успешный cast_vote платит fsync; групповой коммит сглаживает это только под конкурентностью по разным предложениям.
- Per-proposal mutex (docs/01 §5) сериализует операции одного предложения → рабочая нагрузка обязана быть распределена по многим предложениям.
- `voterpool_mcp_requests_total` инкрементируется только в HTTP-слое (`McpHandler.cpp`, `handleMcpPost`) — на уровне dispatch он неподвижен. Наблюдаемые корробораторы в процессе: доменные gauge (`voterpool_agents_total`, …), консенсусные счётчики и RocksDB-тикеры (`voterpool_rocksdb_wal_synced_total` растёт на каждой sync-записи; паттерн двух скрейпов см. tests/integration/test_metrics_semantics.cpp).
- Rate limiting неактивен по умолчанию (enabled: false, спека configuration) — нагрузке ничего не противостоит.
- Один успешный cast_vote расходует слот навсегда (голосование один раз за предложение).

## Goals / Non-Goals

**Goals:**

- Один бинарник `tests/bench/voterpool_bench.cpp`, два сценария (`read`, `write`), совместимый с hot_path_bench стиль вывода (одна JSON-строка с label).
- Воспроизводимость прогона как *методики*: фиксированный пул, отдельный учёт setup, отчуждаемые поля контекста.
- Скромные дефолты (~10 сек замера); тяжёлые прегоны — только флагами и по явному указанию, на отдельной машине.
- Правки docs/00 (NFR-1 без цифры) и docs/10 (реальные имена файлов вместо обещанных).

**Non-Goals:**

- RPS по проводу (HTTP-слой + Drogon): нужен асинхронный генератор нагрузки, которого нет; отложено осознанно (см. Open Questions).
- Интеграция внешних инструментов (wrk/hey/k6).
- Самопитающаяся нагрузка (b): воркеры сами создают предложения — замер становится смесью.
- Изменения продуктового кода ядра, конфигурации, rate limiting.
- Автоматизация перф-прогонов в CI (docs/10 §3.3 прямо исключает).

## Decisions

### D1. Один таргет `voterpool_bench`, режимы через argv

`voterpool_bench <label> <read|write> [флаги]`. Имя совпадает с обещанным в docs/10 — правка документа минимальна.

Альтернативы: расширить hot_path_bench режимом — отвергнуто: это регрессионная линейка p99 с другим контрактом вывода, смешивание затруднит оба использования; два отдельных бинарника — отвергнуто: дублирование setup/reporting либо преждевременная факторизация общей библиотеки ради двух сценариев.

### D2. Уровень измерения — инпроцесс dispatch

Оба сценария гоняют `mcp::dispatchToolForTests` (прецедент hot_path_bench и integration Harness) поверх реального AppContext + временной RocksDB. Это «чистое число движка»: simdjson-парсинг, middleware и сериализация ответа исключены.

Альтернатива — полный стек через E2eEnv + Drogon HttpClient: отвергнута на этот раз; синхронный HttpUtil из tests/common годится для функциональных тестов, но генератор конкурентной нагрузки поверх блокирующего клиента упрётся в клиента, а не в движок.

### D3. Write-нагрузка: фиксированный пул слотов (вариант (а))

Setup создаёт `--agents A` агентов, организации и `--proposals P` предложений (распределены по организациям равномерно), строит вектор всех пар (AgentContext*, proposal_id), перемешивает. Фаза замера: T рабочих потоков забирают следующий слот через `std::atomic<size_t>` (fetch_add), выполняют cast_vote, учитывают исход, пока есть слоты и не истёк дедлайн.

- Уникальность слота гарантируется атомарным индексом — каждый голос засчитан ровно один раз.
- Перемешивание даёт равномерное покрытие предложений → per-proposal mutex не искажает картину.
- Истощение пула раньше таймера — штатный исход: длительность фазы фактическая, RPS = ok / elapsed.
- Setup хронометрируется отдельно (`setup_s`) и в замер не входит.
- Модель консенсуса write-организаций — **CONSENT/EQUAL** (уточнение по ходу apply): MAJORITY закрывает предложение после Y > T/2, и остаток слотов превращается в -32003 (на малом пуле 6×3 это 6 из 18; на дефолтных ~половина пула), что разрушает метрику «успешный cast_vote». CONSENT проходит только последним голосом полного круга — дренаж на 100% успешен по построению. Сценарий read сохраняет MAJORITY: путь дубликата от модели не зависит.

Альтернативы: самопитание (b) — отвергнуто сейчас (смесь create_proposal+cast_vote делает число невоспроизводимым по составу); динамическое пополнение пула в фоне — та же смесь плюс гонки за порогом пополнения.

### D4. Read-нагрузка: три повторяемые операции

Каждая итерация рабочего потока: search_organizations (подстрочный запрос) → get_proposal → дубликат cast_vote с ожидаемым -32003. Все три бесконечно повторяемы, состояния не мутируют. Ожидаемый отказ -32003 — одновременно нагрузка read-mostly пути (lookup+membership+lock) и встроенный сигнал корректности: любой другой код ошибки учитывается отдельно и виден в выводе.

### D5. Управление длительностью и перцентили

Дедлайн по `std::chrono::steady_clock`; проверка перед каждой операцией. Каждый поток копит длительности своих операций (операция блокирующая, closed-loop); вектора сливаются, p50/p99 считаются как в hot_path_bench. Замер закрытого цикла занижает хвостовую задержку под очередью — перцентили информационные, заголовок отчёта — RPS (координационное упущение не корректируется сознательно).

### D6. Дефолты скромные, тяжёлое — явно

| Флаг | Дефолт |
|---|---|
| --threads | hardware_concurrency() |
| --duration | 10 |
| --agents (write) | 300 |
| --proposals (write) | 100 |

30 000 слотов при однопоточном fsync-bound темпе (~1–3k/с) покрывают 10-секундное окно; под высокой конкурентностью пул исчерпается раньше — штатно (D3). Нагрузочные прогоны (большие A/P/T, минуты) возможны флагами; политика — не запускать их рутинно, документируется в --help и tasks.

### D7. Корроборация записи тикером WAL

В write-режиме до и после фазы замера вызывается `db->publishStatisticsToRegistry()`; прирост `voterpool_rocksdb_wal_synced_total` за окно попадает в JSON (`wal_synced_delta`). Физика тикера уточнена по ходу apply: WAL_FILE_SYNCED считает fsync-события, а групповой коммит сливает несколько параллельных sync-записей в одно событие, поэтому при конкурентности delta < ok — НОРМА (замерено: 282 fsync на 500 записей при 4 потоках). Строгая проверка возможна только серийно: при `--threads 1` delta ДОЛЖНА равняться ok, расхождение — предупреждение в stderr без падения. Жёсткие внутренние инварианты (ok + errors == ops; слоты без повторов) проверяются ассертами процесса.

Альтернатива: сверять voterpool_mcp_requests_total — невозможна на этом уровне: счётчик живёт в HTTP-слое и dispatch-вызовы его не двигают. Тикер WRITE_WITH_WAL был бы 1:1 к записям, но его публикация — правка продуктового кода (вне границ изменения).

### D8. Формат вывода

Одна строка JSON в stdout (jsoncpp StreamWriterBuilder, как hot_path_bench):

```
{"label":…,"scenario":"write","threads":8,"agents":300,"proposals":100,
 "slots":30000,"setup_s":12.4,"duration_s":10.0,"ops":21453,"ok":21453,
 "ok_rps":2145.3,"errors":{},"rps":2145.3,"p50_us":…,"p99_us":…,
 "wal_synced_delta":6120}
```

`rps` — все операции в секунду; `ok_rps` — успешные cast_vote в секунду (ключевое число write-режима). Для read: agents/proposals/slots описывают seed-данные, wal_synced_delta отсутствует, errors содержит {"-32003":N}.

## Risks / Trade-offs

- [Числа fsync-bound гуляют между машинами и дисками] → все поля контекста в выводе; сравнивать можно только прогоны одной машины; межмашинное сравнение — качественное.
- [Пул исчерпывается за секунды под высокой конкурентностью] → штатное раннее завершение (D3); для длинных прогонов инструкция: увеличивать --agents/--proposals пропорционально ожидаемому RPS.
- [Setup платит fsync за каждую операцию последовательно] → setup_s отчётся отдельно; дефолты скромные; тяжёлый сетап — цена явного нагрузочного прогона.
- [Closed-loop перцентили занижают хвост] → перцентили вторичны; для хвостовой задержки существует hot_path_bench.
- [MetricsRegistry — глобальный синглтон процесса] → бенчмарк владеет процессом целиком, чужих записей нет; resetForTests не нужен.
- [TTL-воркер и SSE-хаб живут в AppContext] → срок жизни предложений задан с запасом, воркеры стартуют, но на окно замера не влияют; шум виден в wal_synced_delta, не в счётчиках операций.

## Migration Plan

Изменение аддитивное: новый файл + строки в tests/CMakeLists.txt, правки двух документов. Продуктовый код не затронут, отката сверх revert не требуется.

## Open Questions

Нет блокирующих. RPS по проводу (HTTP-уровень) — намеренно отложенная тема для будущего изменения; потребует решения о асинхронном генераторе нагрузки (Drogon coroutine client vs raw sockets vs внешний инструмент).
