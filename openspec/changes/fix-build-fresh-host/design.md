## Context

См. proposal.md — Why. Три дефекта в `build.sh` подтверждены воспроизведением в bash и логом с реальной VPS (ubuntu 22.04, root):

1. **Стр. 86** — `ask()` читает `$NONINTERACTIVE`; переменная инициализируется только флагом `-y/--yes` (стр. 77); при `set -u` интерактивный запуск падает на первом же вопросе.
2. **Стр. 95** — root-ветка `sudo_cmd()` содержит голый литерал `""`: bash исполняет пустую строку как команду → `: command not found`, exit 127.
3. **Стр. 188** — `$s DEBIAN_FRONTEND=noninteractive apt-get install ...`: bash классифицирует слова по позиции **до** расширения; `$s` занимает слот команды, поэтому при пустом `$s` присваивание становится именем команды. С `$s=sudo` работает (sudo сам понимает `VAR=val cmd`), от root — нет. Проверено тестом: `s=""; $s FOO=bar printenv FOO` → `FOO=bar: command not found`; `s=""; $s env FOO=bar printenv FOO` → работает.

Дополнительный фактор маскировки: все вызовы `install_system_packages` обёрнуты в `|| true` / `|| warn` — это отключает `set -e` внутри всей функции, поэтому exit 127 не ронял скрипт сразу, а приводил к каскаду «компилятор не появился».

Ограничения матрицы дистрибутивов: Debian ≤ 11 (gcc-10 без корутин, cmake 3.18) и Ubuntu ≤ 20.04 (gcc-9, cmake 3.16) не могут быть вылечены штатными репозиториями. Решение по ним — fail-fast (см. proposal).

## Goals / Non-Goals

**Goals:**
- Пустой хост из поддерживаемой матрицы (Ubuntu 22.04/24.04, Debian 12/13) доводится `./build.sh [--yes]` до бинарника без ручных шагов, под root и под sudo-пользователем.
- Диагностика остаётся честной: старые дистрибутивы отклоняются одним понятным сообщением до начала установки.

**Non-Goals:**
- Поддержка Debian ≤ 11 / Ubuntu ≤ 20.04 через сторонние репозитории (Kitware, llvm.org) — осознанно отклонено на этапе эксплорации.
- Пересмотр философии `set -euo pipefail` / рефакторинг структуры скрипта — правим только дефектные места.
- Поддержка macOS/BSD, Windows, не-apt семейств меняется только в объёме уже написанного кода (не трогаем).
- Автотесты шелла в CI — верификация контейнерами описана в tasks.md как ручной прогон.

## Decisions

**D1. Инициализация `NONINTERACTIVE=0` в блоке дефолтов (рядом со стр. 21–29), а не `${NONINTERACTIVE:-}` в месте чтения.**
Переменная декларативно объявлена вместе с остальными флагами-состояниями (`ASSUME_YES`, `DO_CLEAN`, ...); место чтения остаётся простым сравнением. Альтернатива (дефолт при каждом чтении) размазывает знание о переменной по коду.

**D2. Root-ветка `sudo_cmd()` возвращает пустой вывод без исполнения: `if [ "$(id -u)" -eq 0 ]; then echo ""; elif have sudo; then echo sudo; fi`.**
Устраняет и ошибку исполнения, и ненулевой код возврата функции (сейчас 127 при root). Альтернатива «просто заменить `""` на `echo ""`» оставляет ветку else с теми же проблемами структуры; явный `elif` делает обе ветки симметричными. Замечание про `|| true`: после фикса функция всегда возвращает 0, зависимость от маскирующей обёртки исчезает.

**D3. Префикс через `env`: `$s env DEBIAN_FRONTEND=noninteractive apt-get install -y $pkgs`.**
Работает при обоих значениях `$s` (`env` есть во всех поддерживаемых дистрибутивах; `sudo env VAR=val cmd` — валидно). Альтернативы:
- *подоболочка с export* `(export DEBIAN_FRONTEND=noninteractive; $s apt-get install ...)` — тоже корректно, но добавляет вложенность и второй уровень кавычек при будущих правках;
- *всегда требовать sudo* — ломает сценарий root-контейнеров, главный для VPS-деплоя.
Проверено живым тестом (оба варианта префикса дают `noninteractive`).

**D4. Fail-fast по версии дистрибутива — гейт только на путь автоустановки, не на весь скрипт.**
Хелпер `distro_min_version_met()` (debian ≥ 12, ubuntu ≥ 22.04; прочие семейства — считаем пригодными и полагаемся на существующие пробы компилятора/cmake). Вызывается перед каждым местом, где скрипт собирался бы что-то ставить ради тулчейна (строки ~267 и ~278): если дистрибутив заведомо недостаточен — `err` с конкретикой («обнаружен Debian 11; требуется Debian ≥ 12 или Ubuntu ≥ 22.04») и `exit 1` вместо `confirm`. Хост с самосборным тулчейном проходит пробы и продолжает работать независимо от возраста дистрибутива. Альтернатива «жёсткий гейт в шапке скрипта по версии ОС» отвергнута: она бы сломала легитимный сценарий опытного пользователя с собственным тулчейном.

**D5. Подсказка при неизвестном флаге — нормализация черт и точное сравнение.**
Кандидат нормализуется снятием ведущих `-` и сверяется со списком известных имён опций (`yes`, `debug`, `jobs`, ...) без учёта числа черт; при совпадении выводится «did you mean --yes?». Полный Левенштейн не нужен — реальный кейс исчерпывается числом черт.

## Risks / Trade-offs

- [Правки в `case`-ветке apt-get затрагивают общий путь установки] → ветка одна, поведение с `$s=sudo` сохранено (`sudo env ...` эквивалентен прежнему `sudo VAR=val ...`), проверяется контейнером под обоими пользователями.
- [Fail-fast может ложно сработать на нестандартном хосте (backports-тулчейн на Debian 11)] → нет: гейт стоит только перед попыткой установки; если пробы пройдены, установка не нужна и гейт не достигается.
- [Верификация интерактивного режима автоматикой затруднена: `ask()` читает `/dev/tty`] → интерактивный сценарий проверяется вручную на реальной VPS / `docker run -ti`; контейнерная автоматика покрывает `--yes` и piping-режим.
- [`librocksdb-dev` и др. могут отсутствовать в свежих релизах (Debian 13)] → прогон матрицы контейнеров в tasks.md выявит пробелы списка пакетов до мержа; при отсутствии пакета — отдельное решение, вне этого изменения.

## Migration Plan

Изменение обратно совместимо: сигнатуры функций и CLI не меняются, новые сообщения появляются только там, где раньше был сбой. Развёртывание = замена `build.sh` в репозитории. Откат — git revert одного файла.
