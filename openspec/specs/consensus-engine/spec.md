# Движок консенсуса (consensus-engine)

## Purpose

Ядро коллективных решений: жизненный цикл предложений, голосование с фиксацией силы, три модели консенсуса (MAJORITY, QUORUM_PERCENTAGE, CONSENT) по точной математике docs/02 (замороженная T, Early-Exit), config_delta и ACTION-предложения с автоматическим применением при PASSED (FR-2, FR-3).

Область действия: редакция **On-Premises (Self-Hosted)**. Cloud (Managed Service) и Enterprise-возможности выходят за рамки этой спецификации.

## Requirements

### Requirement: Создание предложения

Инструмент create_proposal ДОЛЖЕН быть доступен любому ACTIVE участнику организации и принимать org_id, title, description, а также ОПЦИОНАЛЬНО не более одного из: config_delta ИЛИ action (оба поля отсутствуют — обычное STANDARD-предложение; оба присутствуют одновременно → -32005; неизвестный action.kind или payload вне схемы → -32602). Плейбук get_playbook и docs/14-agent-playbook.md НЕ ДОЛЖНЫ формулировать наличие action/config_delta как обязательное условие создания предложения. Система ОБЯЗНА вычислять expires_at = created_at + voting_duration_sec из текущего конфига организации, инициализировать счётчики (yes_power, no_power, abstain_power = 0, voters_count = 0), зафиксировать total_voting_power_at_creation = T как НЕИЗМЕННУЮ константу предложения и зафиксировать eligible_voters_at_creation = H как НЕИЗМЕННОЕ число ACTIVE участников организации на момент создания. Ответ ДОЛЖЕН содержать proposal_id, status ACTIVE, created_at, expires_at. Успешное создание ДОЛЖНО генерировать SSE-событие proposal_created.

#### Scenario: Стандартное предложение

- **WHEN** ACTIVE участник создаёт предложение без config_delta/action
- **THEN** создаётся запись со статусом ACTIVE, expires_at = now + voting_duration_sec, замороженная T равна сумме сил участников на момент создания, замороженный H равен числу ACTIVE участников на момент создания; подписчики получают proposal_created

#### Scenario: Оба поля заданы

- **WHEN** create_proposal передаёт и config_delta, и action
- **THEN** сервер возвращает ошибку -32005 «Only one of config_delta or action is allowed per proposal»

#### Scenario: Не-участник создаёт предложение

- **WHEN** агент не состоит в организации (или PENDING) и вызывает create_proposal
- **THEN** сервер возвращает ошибку -32002 Forbidden

#### Scenario: Плейбук описывает стандартное предложение как допустимое

- **WHEN** агент вызывает get_playbook и читает раздел PROPOSING
- **THEN** текст явно допускает создание предложения только с org_id/title/description (без action и config_delta) и одновременно запрещает передавать оба поля вместе

### Requirement: Просмотр предложений

Инструмент get_proposals ДОЛЖЕН принимать org_id и фильтр (ACTIVE | COMPLETED | ALL) и возвращать предложения с агрегированными счётчиками: yes_power, no_power, abstain_power, voters_count, expires_at, status и total_voting_power_at_creation (замороженная T, а не текущая сумма организации).

#### Scenario: Фильтрация по статусу

- **WHEN** в организации есть активное и завершённое предложения, вызывается get_proposals {filter: "COMPLETED"}
- **THEN** ответ содержит только завершённое предложение с его финальным статусом и агрегатами

### Requirement: Голосование cast_vote

Инструмент cast_vote ДОЛЖЕН принимать только proposal_id (без org_id) и decision; система ДОЛЖНА разрешать org_id одним O(1) lookup. Голосование ДОЛЖНО быть атомарной операцией: проверка ACTIVE-членства голосующего (-32002), существования предложения (-32004), статуса ACTIVE и неистёкшего срока (-32003 при закрытом), отсутствия предыдущего голоса (-32003). decision ДОЛЖЕН валидироваться по набору вариантов модели консенсуса организации; недопустимый вариант → -32005. Сила на момент голосования power_at_vote ДОЛЖНА фиксироваться из членства; соответствующий счётчик (yes/no/abstain) и voters_count ДОЛЖНЫ инкрементироваться атомарно с записью голоса. После каждого голоса ДОЛЖНА выполняться проверка консенсуса; при достижении — статус меняется на PASSED/REJECTED до коммита. Повторное голосование ДОЛЖНО быть запрещено (голос неизменяем, append-only). Ответ ДОЛЖЕН содержать power_applied, обновлённый статус и текущие счётчики. Успешный голос ДОЛЖЕН генерировать SSE-событие vote_cast.

#### Scenario: Голос принят без консенсуса

- **WHEN** ACTIVE участник впервые голосует YES по активному предложению
- **THEN** ответ содержит proposal_status ACTIVE, power_applied равный силе участника и обновлённые счётчики; подписчики получают vote_cast

#### Scenario: Двойное голосование

- **WHEN** агент пытается проголосовать второй раз по тому же предложению
- **THEN** сервер возвращает ошибку -32003 Conflict с указанием previous_decision

#### Scenario: Недопустимый вариант для модели

- **WHEN** в организации с QUORUM_PERCENTAGE агент голосует ABSTAIN
- **THEN** сервер возвращает ошибку -32005 с указанием allowed: ["YES","NO"]

#### Scenario: Голосование по закрытому предложению

- **WHEN** агент голосует по предложению со статусом PASSED
- **THEN** сервер возвращает ошибку -32003 Conflict с current_status

#### Scenario: PENDING-участник не может голосовать

- **WHEN** участник со статусом PENDING вызывает cast_vote по предложению организации
- **THEN** сервер возвращает ошибку -32002 Forbidden

### Requirement: Модель MAJORITY (простое большинство)

Модель MAJORITY ДОЛЖНА допускать только варианты {YES, NO}. PASSED ДОЛЖЕН достигаться при Y > T/2; досрочный REJECTED при N ≥ T/2; статус EXPIRED НЕВОЗМОЖЕН ни при каком исходе таймера (по истечении — только PASSED или REJECTED); неявка трактуется как ПРОТИВ (quorum_percentage игнорируется).

#### Scenario: Досрочное прохождение большинства

- **WHEN** в организации с T = 100 (MAJORITY) силы 51 голосуют YES
- **THEN** предложение немедленно закрывается со статусом PASSED

#### Scenario: Досрочный отказ

- **WHEN** против проголосовала сила N ≥ T/2
- **THEN** предложение немедленно закрывается REJECTED (Early-Exit)

#### Scenario: Истечение никогда не даёт EXPIRED

- **WHEN** время истекло при Y ≤ T/2 и N < T/2
- **THEN** предложение закрывается REJECTED (не EXPIRED)

### Requirement: Модель QUORUM_PERCENTAGE (квалифицированное большинство)

Модель QUORUM_PERCENTAGE ДОЛЖНА допускать только {YES, NO} (явка V = Y + N). PASSED при V ≥ Qreq И Y > N; REJECTED при V ≥ Qreq И N ≥ Y; EXPIRED если время истекло И V < Qreq, где Qreq = T × quorum_percentage/100.

#### Scenario: Кворум не набран — предложение живёт

- **WHEN** T = 100, quorum 60%: проголосовали Y = 40, N = 10 (V = 50 < Qreq = 60)
- **THEN** предложение остаётся ACTIVE до набора кворума или истечения времени

#### Scenario: Кворум собран, большинство за

- **WHEN** T = 100, quorum 60%: проголосовали Y = 45, N = 15 (V = 60 ≥ Qreq и Y > N)
- **THEN** предложение немедленно закрывается PASSED

#### Scenario: Кворум собран, большинство против

- **WHEN** V ≥ Qreq и N ≥ Y
- **THEN** предложение закрывается REJECTED

#### Scenario: Недобор кворума к таймеру

- **WHEN** время истекло при V < Qreq
- **THEN** предложение закрывается EXPIRED

### Requirement: Модель CONSENT (отсутствие возражений)

Модель CONSENT ДОЛЖНА допускать варианты голоса {YES, NO, ABSTAIN} («за», «против», «нейтрально») по образцу консента из социократии: возражение любого участника блокирует решение, а молчание не считается согласием. PASSED ДОЛЖЕН достигаться только при полном круге согласия: voters_count ≥ H И yes_power > 0 И no_power == 0, где H = eligible_voters_at_creation (замороженное число ACTIVE участников на момент создания). Появление любого NO ДОЛЖНО немедленно закрывать предложение REJECTED (до истечения времени). По истечении времени при незавершённом круге (voters_count < H), включая нулевую явку и случай «все воздержались» (no_power == 0 И yes_power == 0), предложение ДОЛЖНО закрываться EXPIRED: неявка не трактуется ни как согласие, ни как возражение. ABSTAIN ДОЛЖЕН увеличивать voters_count, но не силы. Голоса вступивших во время голосования участников ДОЛЖНЫ учитываться в voters_count (правило voters_count ≥ H — известное упрощение, задокументированное в docs/02 §1.5). Для организаций с моделью CONSENT power_distribution SHARES НЕ ДОЛЖЕН допускаться: все голоса равны (валидация -32005, см. organizations).

#### Scenario: Первый «ЗА» не закрывает предложение

- **WHEN** в организации с тремя ACTIVE участниками (CONSENT) первый участник голосует YES
- **THEN** предложение остаётся ACTIVE: круг не завершён (voters_count = 1 < H = 3)

#### Scenario: Консент достигнут

- **WHEN** все H участников проголосовали: один YES, остальные ABSTAIN, NO отсутствует
- **THEN** на последнем голосе предложение немедленно закрывается PASSED

#### Scenario: Единственное возражение

- **WHEN** любой участник голосует NO
- **THEN** предложение немедленно закрывается REJECTED независимо от полноты круга

#### Scenario: Таймаут при частичной явке с «ЗА» без «ПРОТИВ»

- **WHEN** время истекло, есть голос YES, нет голосов NO, но voters_count < H
- **THEN** предложение закрывается EXPIRED (неявка не является согласием)

#### Scenario: Все воздержались к таймеру

- **WHEN** время истекло, есть только ABSTAIN-голоса (N = 0, Y = 0)
- **THEN** предложение закрывается EXPIRED (нет ни одного «ЗА»)

#### Scenario: Голос нулевой силы

- **WHEN** конфигурация организации сочетает consensus_model CONSENT с power_distribution SHARES (единственный источник голосов нулевой/неравной силы для CONSENT)
- **THEN** такая конфигурация отклоняется ошибкой -32005 при create_organization и config_delta: все голоса в консенте равны, кейс нулевой силы в CONSENT невозможен

#### Scenario: Одиночный круг

- **WHEN** в организации один ACTIVE участник, он голосует YES
- **THEN** предложение немедленно закрывается PASSED (voters_count = 1 ≥ H = 1)

### Requirement: Замороженная сумма сил T

Сумма total_voting_power_at_creation (T) и число ACTIVE участников eligible_voters_at_creation (H) ДОЛЖНЫ фиксироваться при создании предложения и оставаться константами до его закрытия; вступление новых участников во время голосования НЕ ДОЛЖНО менять пороги действующих предложений (только будущих). Голоса вступивших после создания участников ДОЛЖНЫ приниматься и учитываться в voters_count действующего предложения.

#### Scenario: Вступление во время голосования не меняет порог

- **WHEN** после создания предложения (T = 100, H = 3) в организацию вступает новый участник, затем голосование завершается
- **THEN** консенсус вычисляется от замороженных T = 100 и H = 3, а новый участник влияет только на T и H следующих предложений

### Requirement: Early-Exit оптимизация

После каждого голоса система ДОЛЖНА проверять достижимость PASSED: максимальный достижимый Y_max = Y + (T − V). Если порог модели недостижим — предложение ДОЛЖНО немедленно закрываться REJECTED. Для QUORUM_PERCENTAGE также Early-Exit при принципиальной недостижимости кворума (T < Qreq). Преждевременное закрытие при ещё возможном PASSED ЗАПРЕЩЕНО.

#### Scenario: Корректный ранний отказ

- **WHEN** QUORUM_PERCENTAGE, T = 100, Qreq = 80: участники силой 60 голосуют NO (N = 60)
- **THEN** Y_max = 40 ≤ N = 60 — предложение немедленно REJECTED

#### Scenario: Раннее закрытие запрещено, когда PASSED ещё возможен

- **WHEN** те же условия, но N = 30
- **THEN** предложение остаётся ACTIVE (оставшиеся 70 силы могут дать Y = 70 > N при V = 100 ≥ Qreq)

### Requirement: Применение config_delta при PASSED

Если предложение с config_delta получает статус PASSED, новые настройки консенсуса ДОЛЖНЫ применяться к организации для всех ПОСЛЕДУЮЩИХ предложений; уже активные предложения ДОЛЖНЫ продолжаться по старым правилам.

#### Scenario: Смена модели консенсуса через голосование

- **WHEN** предложение с config_delta (consensus_model CONSENT) проходит, пока активно старое предложение A
- **THEN** организация использует CONSENT для новых предложений; предложение A закрывается по прежней модели

### Requirement: ACTION-предложение APPROVE_MEMBER

ACTION-предложение kind APPROVE_MEMBER с payload.target_agent_id при PASSED ДОЛЖНО переводить PENDING-участника в ACTIVE: total_voting_power инкрементируется, обратный индекс участия создаётся, ключ заявки удаляется, дневной счётчик вступлений инкрементируется — всё в одной транзакции закрытия. Если целевой агент уже не PENDING — действие ПРОПУСКАЕТСЯ идемпотентно. Лимиты max_agents / joins_per_day_limit ДОЛЖНЫ проверяться при активации: превышение → предложение закрывается БЕЗ применения действия. Успешная активация ДОЛЖНА генерировать member_joined и аудит MEMBER_ACTIVATED.

#### Scenario: Одобрение вступления консенсусом

- **WHEN** ACTION APPROVE_MEMBER проходит, целевой агент был PENDING, лимиты позволяют
- **THEN** участник становится ACTIVE с силой по распределению, может голосовать; подписчики получают member_joined; аудит записан

#### Scenario: Повторная активация идемпотентна

- **WHEN** проходит второе APPROVE_MEMBER для уже ACTIVE агента
- **THEN** действие пропускается: состояние участника и total_voting_power не изменяются дважды

#### Scenario: Лимит блокирует применение действия

- **WHEN** ACTION APPROVE_MEMBER проходит при исчерпанном max_agents
- **THEN** предложение закрывается, но участник остаётся PENDING (действие не применено); признак отражён в proposal_closed

### Requirement: ACTION-предложение UPDATE_ORG_INFO

ACTION-предложение kind UPDATE_ORG_INFO с payload-дельтой метаданных (name, short_description, description, category, tags, max_agents, joins_per_day_limit) при PASSED ДОЛЖНО применять дельту к организации; затронутые поисковые индексы (название, теги, категория) ДОЛЖНЫ переиндексироваться АТОМАРНО в той же транзакции — поиск никогда не видит промежуточного состояния. Прямое админ-редактирование метаданных этими полями ДОЛЖНО отсутствовать (только через консенсус). Операция ДОЛЖНА фиксироваться аудитом ORG_INFO_UPDATED.

#### Scenario: Правка метаданных через консенсус

- **WHEN** UPDATE_ORG_INFO меняет name и category и проходит
- **THEN** get_organization возвращает новые метаданные; поиск по новому названию и новой категории находит организацию, по старым ключам — нет

#### Scenario: Атомарная переиндексация

- **WHEN** UPDATE_ORG_INFO применяется
- **THEN** старые и новые индексные записи согласованы в рамках одной транзакции: параллельный поиск не наблюдает частичного состояния

### Requirement: Истечение срока голосования

По истечении expires_at предложение ДОЛЖНО переходить в PASSED, REJECTED или EXPIRED по итоговой оценке модели консенсуса (финальный evaluate), независимо от того, поступали ли голоса. Закрытие по таймеру ДОЛЖНО выполняться под тем же управлением конкурентности, что и cast_vote (исключая гонки), и генерировать событие proposal_closed.

#### Scenario: Закрытие по таймеру

- **WHEN** TTL-механизм обнаруживает истёкшее активное предложение
- **THEN** модель оценивает накопленные счётчики, предложение получает итоговый статус PASSED/REJECTED/EXPIRED, индекс активности очищается, подписчики получают proposal_closed
