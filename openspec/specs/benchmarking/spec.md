# Бенчмарки пропускной способности (benchmarking)

## Purpose

Бенчмарки пропускной способности движка Voterpool: воспроизводимое измерение RPS на уровнях инпроцессного диспетчера (CPU-потолок) и синхронной WAL-записи (fsync-пол), с отчуждаемым JSON-выводом для сравнения прогонов между машинами.

## Requirements

### Requirement: Бенчмарк-таргет пропускной способности

Сборка ДОЛЖНА предоставлять отдельный исполняемый таргет `voterpool_bench`, принимающий имя прогона (label) и сценарий (`read` или `write`). Таргет НЕ ДОЛЖЕН входить в дефолтный набор ctest и ДОЛЖЕН собираться только по явному запросу (EXCLUDE_FROM_ALL), согласно docs/10 §3.3.

#### Scenario: Таргет вне дефолтного тестового набора

- **WHEN** выполняется полный прогон ctest после сборки тестов
- **THEN** бенчмарк не запускается автоматически; его бинарник доступен в каталоге сборки для ручного запуска

### Requirement: Сценарий read — чистый потолок движка

Сценарий `read` ДОЛЖЕН измерять устойчивую пропускную способность инпроцессного dispatch на конкурентных повторяемых операциях без мутаций состояния: get_proposal, search_organizations и отклоняемый дубликат cast_vote (ошибка -32003). Число потоков ДОЛЖНО задаваться флагом --threads (по умолчанию — аппаратная конкурентность). Прогон ДОЛЖЕН ограничиваться длительностью --duration (по умолчанию 10 секунд).

#### Scenario: Устойчивый замер без износа состояния

- **WHEN** сценарий read завершается по таймеру
- **THEN** все выполненные операции были либо успешными чтениями, либо детерминированными отказами -32003, состояние базы осталось консистентным, а результат содержит достигнутый RPS

#### Scenario: Конкурентность настраивается

- **WHEN** запуск выполнен с --threads 4
- **THEN** нагрузка создаётся ровно четырьмя рабочими потоками, и это число отражено в выводе

### Requirement: Сценарий write — пол sync-WAL записи

Сценарий `write` ДОЛЖЕН измерять пропускную способность успешного cast_vote с синхронной WAL-записью на конечном пуле слотов голосования: перед замером создаются --agents агентов и --proposals предложений, образующие пул уникальных пар (агент, предложение); рабочие потоки разбирают пул через атомарный счётчик до истощения или истечения --duration. Время подготовки пула ДОЛЖНО измеряться отдельно от времени замера. Отчёт ДОЛЖЕН содержать отдельное поле ok_rps — отношение числа успешных cast_vote к фактической длительности фазы. Запуск с --threads 1 ДОЛЖЕН давать интерпретируемое значение «RPS на одно ядро при sync WAL». Рабочая нагрузка ДОЛЖНА быть свободна от раннего консенсуса: модель организаций сценария выбирается так, чтобы предложение не закрывалось до полного дренажа пула (иначе остаток слотов превращается в отказы и искажает метрику успешных записей).

#### Scenario: Однопоточная цена sync WAL

- **WHEN** сценарий write запущен с --threads 1 и пулом слотов
- **THEN** результат содержит RPS успешных cast_vote за вычетом времени setup, и каждый учтённый слот использован ровно один раз

#### Scenario: Истощение пула короче таймера

- **WHEN** пул слотов исчерпан до истечения --duration
- **THEN** замер завершается сразу, RPS считается по фактической длительности фазы замера, а не по --duration

#### Scenario: Скромные дефолты

- **WHEN** сценарии запущены без флагов объёма
- **THEN** используются скромные значения пула (порядка сотен агентов и сотен предложений) и длительность около 10 секунд; тяжёлые прогоны возможны только при явном переопределении флагов

### Requirement: Отчуждаемый формат результата

Бенчмарк ДОЛЖЕН печатать ровно одну строку JSON, содержащую как минимум: label, сценарий, число потоков, длительность фазы замера, суммарное число операций, счётчики успешных и ошибочных операций (с разбивкой по кодам), достигнутый RPS и перцентили p50/p99 задержки операции. Формат ДОЛЖЕН быть совместим по стилю с существующим hot_path_bench (label + плоский JSON).

#### Scenario: Машинно-читаемый итог

- **WHEN** любой сценарий завершается
- **THEN** stdout содержит одну валидную JSON-строку, поля которой позволяют сравнить два прогона на разных машинах без доступа к их stderr

#### Scenario: Корроборация записи тикером WAL

- **WHEN** сценарий write завершает фазу замера и выполнены два скрейпа статистики хранилища (до и после фазы) в том же процессе
- **THEN** результат содержит прирост тикера синхронизации WAL (voterpool_rocksdb_wal_synced_total) за окно замера; при --threads 1 этот прирост РАВЕН числу успешных cast_vote фазы (серийные записи синхронизируются поодиночке), а при большей конкурентности прирост отражает число групповых коммитов WAL и носит информационный характер
