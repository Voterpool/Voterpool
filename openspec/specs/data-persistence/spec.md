# Персистентность (data-persistence)

## Purpose

Слой персистентности: гарантии долговечности и атомарности на RocksDB, контроль конкурентности per-proposal, неизменяемый журнал аудита, версионирование схемы с автоматическими миграциями и бэкап/восстановление через Checkpoints (docs/01, docs/12, docs/13; NFR-2).

Область действия: редакция **On-Premises (Self-Hosted)**. Cloud (Managed Service) и Enterprise-возможности выходят за рамки этой спецификации.

## Requirements

### Requirement: Долговечность и восстановление состояния

Все записи (агенты, организации, членства, предложения, голоса) ДОЛЖНЫ синхронно коммититься в хранилище с включённым WAL. После рестарта сервиса состояние консенсусов, профилей и членств ДОЛЖНО полностью восстанавливаться (автоматический replay журнала после сбоя).

#### Scenario: Восстановление после рестарта

- **WHEN** записаны агенты, организации, предложения и голоса, затем процесс останавливается и запускается заново
- **THEN** все сущности читаемы, агрегаты предложений и статусы идентичны состоянию до остановки

### Requirement: Атомарность мутаций

Каждая составная мутация (голос + счётчики + индексы + аудит; активация участника + total_voting_power + очистка заявки; роспуск + чистка индексов) ДОЛЖНА выполняться единой атомарной транзакцией. Частичное состояние после сбоя между шагами НЕДОПУСТИМО: сумма счётчиков предложения всегда равна сумме сил зафиксированных голосов.

#### Scenario: Нет частичного состояния при голосовании

- **WHEN** операция голосования прерывается сбоем хранилища в любой момент
- **THEN** после восстановления либо полный эффект голоса виден, либо его нет вовсе; инвариант «сумма счётчиков = сумма power_at_vote» не нарушен

### Requirement: Конкурентный контроль per-proposal

Все операции чтение-модификация-запись над предложением (cast_vote, закрытие по таймеру и закрытие при роспуске организации) ДОЛЖНЫ сериализоваться по proposal_id; операции над РАЗНЫМИ предложениями ДОЛЖНЫ выполняться параллельно. Потерянные обновления счётчиков ЗАПРЕЩЕНЫ; ровно один агент = один голос; ровно одно закрытие предложения при гонке голоса и таймера. Блокировка предложения ДОЛЖНА удерживаться до завершения коммита записи с терминальным статусом; удаление записи блокировки ДОЛЖНО выполняться только после успешного коммита терминального статуса. Внутри критической секции состояние предложения И статус его организации ДОЛЖНЫ перепроверяться из хранилища: голос в распущенную организацию ДОЛЖЕН отклоняться (-32004), голос в уже закрытое предложение — -32003. Порядок блокировки ДОЛЖЕН исключать взаимные тупики (не более одного proposal-замока и одного org-замка на операцию, порядок proposal → организация).

#### Scenario: Ноль потерянных обновлений

- **WHEN** N потоков одновременно голосуют по одному предложению разными решениями
- **THEN** финальные yes/no/abstain_power точно равны суммам принятых голосов, каждый агент учтён один раз

#### Scenario: Гонка cast_vote против закрытия по таймеру

- **WHEN** истекает expires_at в момент, когда агент отправляет голос
- **THEN** операции сериализуются: предложение закрывается ровно один раз, итоговый статус корректен для модели, двойного применения последствий нет

#### Scenario: Гонка cast_vote с роспуском организации

- **WHEN** агент отправляет голос в момент выполнения dissolve_organization для той же организации
- **THEN** операции сериализуются: либо голос полностью зафиксирован до закрытия предложения роспуском (и учтён в итоговых счётчиках EXPIRED-записи), либо отклонён ошибкой -32003/-32004; предложение остаётся закрытым ровно один раз, resurrection ACTIVE после DISSOLVED невозможна

#### Scenario: Эффекты PASSED-предложения не переживают роспуск

- **WHEN** предложение достигает консенсуса одновременно с роспуском организации, и роспуск фиксируется раньше
- **THEN** предложение закрывается со своим консенсусным статусом, но config_delta и ACTION (активация участника, правка метаданных) НЕ применяются к распущенной организации

### Requirement: Сериализация мутаций организации

Составные мутации состояния организации — активация вступления (проверка max_agents и joins_per_day_limit + запись членства + инкремент дневного счётчика + пересчёт total_voting_power), выход участника, передача прав администратора, изменение силы голоса, создание предложения (чтение замороженных T/H), роспуск (закрытие предложений + смена статуса + чистка индексов) и применение эффектов PASSED-предложения (config_delta, ACTION) — ДОЛЖНЫ выполняться критических секциях, сериализованных по идентификатору организации. Две конкурентные мутации одной организации НЕ ДОЛЖНЫ терять обновления (last-write-wins по устаревшей копии записи ЗАПРЕЩЁН): итоговое total_voting_power ДОЛЖНО равняться сумме сил ACTIVE участников после применения всех завершённых операций, а число фактических активаций НЕ ДОЛЖНО превышать установленные лимиты. Порядок блокировок ДОЛЖЕН быть единым (сначала блокировка предложения, затем блокировка организации) и исключать взаимные тупики; держатель блокировки организации НЕ ДОЛЖЕН ожидать блокировок предложений. Одновременное голосование за разные предложения одной организации ДОЛЖНО оставаться параллельным.

#### Scenario: Конкурентные вступления при лимите 1

- **WHEN** два агента одновременно вызывают join_organization для OPEN-организации с joins_per_day_limit = 1 и свободным max_agents
- **THEN** ровно одна операция возвращает ACTIVE, вторая получает -32005; дневной счётчик вступлений равен 1, total_voting_power увеличен ровно на одну силу

#### Scenario: Ноль потерянных обновлений total_voting_power

- **WHEN** N операций (вступления, выходы, update_voting_power) выполняются concurrently над одной организацией
- **THEN** после их завершения total_voting_power равен сумме voting_power всех ACTIVE участников; ни один инкремент/декремент не потерян

#### Scenario: Гонка смены силы с лимитом 100%

- **WHEN** ADMIN параллельно выполняет две операции update_voting_power, каждая из которых по отдельности укладывается в 100%, а вместе превышают
- **THEN** не более одной операции успешно применена; сумма сил участников не превышает 100% (+допуск на погрешность); отклонённая операция получает -32005 с attempted_sum

### Requirement: Неизменяемый журнал аудита

Каждое административное или консенсусное изменение (смена силы, активация участника, передача админа, правка метаданных организации, смена конфига) ДОЛЖНО записываться в append-only журнал аудита ТЕМ ЖЕ атомарным пакетом, что и сама мутация («нет действия без аудита»). Записи журнала НИКОГДА не удаляются, включая роспуск организации, и ДОЛЖНЫ читаться по организации в хронологическом порядке.

#### Scenario: Аудит следует за действием

- **WHEN** ADMIN меняет voting_power участника
- **THEN** в журнале появляется запись POWER_CHANGED со старым/новым значением и инициатором, неотделимая от самой мутации

#### Scenario: История переживает роспуск

- **WHEN** организация распущена, затем запрашивается её история аудита
- **THEN** все записи сохранены и читаемы

### Requirement: Версионирование схемы БД

Хранилище ДОЛЖНО хранить целочисленную версию схемы. При создании новой БД — записать текущую версию бинарника. При каждом старте: версия ниже → выполнить цепочку миграций до текущей ДО подъёма воркеров и HTTP; версия равна → обычный старт; версия выше бинарника → фатальный отказ: критический лог и завершение процесса с кодом 1 до открытия сервера (даунгрейд не поддерживается).

#### Scenario: Инициализация новой базы

- **WHEN** движок стартует с пустой директорией хранилища
- **THEN** база создаётся с версией схемы текущего бинарника и сервер поднимается

#### Scenario: Gate «данные новее бинарника»

- **WHEN** движок открывает базу с версией схемы больше своей
- **THEN** процесс завершается с кодом 1 с понятным сообщением, сервер не открывается

### Requirement: Идемпотентные возобновляемые миграции

Каждый шаг миграции ДОЛЖЕН быть идемпотентным: версия повышается только после успешного завершения шага; падение посреди миграции → рестарт дозавершает шаг, пропуская уже преобразованные записи. Новые поля ДОЛЖНЫ получать значения по умолчанию; неизвестные поля ДОЛЖНЫ сохраняться (полный parse-mutate-serialize). Если шаг затрагивает проиндексированные поля — переиндексация обязана идти теми же пакетами. Число преобразованных записей ДОЛЖНО учитываться метрикой миграций.

#### Scenario: Возобновление прерванной миграции

- **WHEN** процесс падает посреди миграции v1→v2 и перезапускается
- **THEN** шаг завершается заново без дублей и порчи данных; версия становится 2

#### Scenario: Сохранение неизвестных полей

- **WHEN** миграция преобразует записи, содержащие поля, которых нет в схеме текущей версии
- **THEN** эти поля сохраняются в значениях после миграции

### Requirement: Бэкапы через согласованные снапшоты

CLI-команда `voterpool checkpoint --config <path> --path <dir>` ДОЛЖНА создавать согласованный point-in-time снимок средствами механизма checkpoints хранилища на живой БД, работать offline (воркеры и HTTP не поднимаются), завершаться кодом 0 при успехе / 1 при ошибке (stderr). Команда ОБЯЗАНА отказываться снимать копию больной базы (не открылась или corruption). При работающем на том же пути движке команда ДОЛЖНА получить ошибку блокировки. Развёрнутый из снимка каталог ДОЛЖЕН открываться движком со всеми читаемыми данными и штатно проходить процедуру миграций при более новом бинарнике.

#### Scenario: Снимок остановленного движка

- **WHEN** `voterpool checkpoint` выполняется на остановленном движке
- **THEN** создаётся согласованный каталог-снимок, процесс завершается с кодом 0

#### Scenario: Отказ на деградировавшей базе

- **WHEN** база повреждена (corruption)
- **THEN** checkpoint отказывает с ошибкой и кодом 1, снимок не создаётся

#### Scenario: Восстановление из снимка

- **WHEN** содержимое снимка развёрнуто в новую директорию хранилища и движок запущен
- **THEN** база открывается, все данные читаемы, состояние соответствует моменту снимка

### Requirement: Изоляция данных организаций

Доступ к данным предложений и голосов ДОЛЖЕН требовать org_id, совпадающий с org_id самого объекта; агент организации A НЕ ДОЛЖЕН получать доступ к данным организации B даже при знании их идентификаторов.

#### Scenario: Кросс-тенантный доступ запрещён

- **WHEN** участник организации A пытается прочитать/проголосовать за предложение организации B
- **THEN** проверка членства отсекает запрос ошибкой -32002
